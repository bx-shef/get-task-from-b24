## Стек

Зафиксирован владельцем 2026-08-26 — тот же, что в `client-bank-alfa-by`, минус фронтенд
(интерфейса у сервиса нет):

| Что | Чем | Почему именно так |
|---|---|---|
| рантайм | **Node 22 LTS** + **pnpm** (через corepack, версия в `packageManager`) | как в соседнем проекте: одни привычки, один деплой |
| сервер | **Nitro** (без Nuxt) | нужны только HTTP-роуты; фронтенд-фреймворк здесь лишний слой |
| база | **Postgres** | токены порталов продлеваются в рантайме, журнал переносов обязан переживать перезапуск |
| очередь | **Redis + BullMQ** | события Б24 **не ретраятся** — приём и обработка обязаны разъехаться |
| клиент Б24 | **`@bitrix24/b24jssdk`** (официальный SDK) | ✅ переехали 2026-09-15: `B24Hook` — наш портал по вебхуку, `B24OAuth` — порталы клиентов. Транспорт и учёт лимитов портала — его; продление токенов, классификация ошибок и запрет редиректов — наши (`src/b24/sdk.ts`) |
| логи и алерты | свой `src/notify/telegram.ts`; `TelegramHandler` из SDK **не берём** | ⚠ Его форматтер вставляет текст сообщения в HTML-шаблон **без экранирования** (экранируются только `context`/`extra`), а `parse_mode` жёстко `HTML`. Проверено на 2.1.0 и перепроверено на 2.2.0 при переезде — поведение то же. Заголовок вида `Счёт < 100 & доставка` уехал бы в разметку как есть, а Телеграм отвечает на такое 400. Брать можно только со своим экранированием до вызова, а это ровно та работа, которую наш модуль уже делает тем, что шлёт без `parse_mode` |
| интерфейсы (когда появятся) | **`@bitrix24/b24ui`** — UI-kit Битрикс24, Vue/Nuxt ([док](https://bitrix24.github.io/b24ui/)) | решение владельца 2026-08-27, на вырост: интерфейса у сервиса пока нет. ⚠ Он под Vue (Nuxt опционален), а у нас Nitro без фронтенд-фреймворка — первый же экран добавляет в стек Vue и сборку фронтенда. ⚠ Публичный npm по имени `@bitrix24/b24ui` отдал 404 (проверено 2026-08-27) — источник пакета уточняем к началу работ над UI |
| тесты | **Vitest** | |
| линт | **ESLint** | |

⚠ **`typescript` ограничен линией 6.x** (`^6.0.3`), и мажор у него в `ignore` у
Dependabot. `typescript-eslint` отказывается работать с TS 7 («does not support TS 7.0»),
то есть на последней версии линт не запускается вообще. Снимать ограничение — когда
`typescript-eslint` научится TS 7, и не раньше.

⚠ **Очередь здесь не «для масштаба», а по существу задачи.** Обработчик обязан ответить
200 до всякой работы, иначе задача клиента теряется молча и навсегда.

## Команды

| Команда | Что делает |
|---|---|
| `corepack enable && pnpm install` | установка зависимостей |
| `docker compose up -d db redis` | локальные Postgres и Redis |
| `pnpm dev` | дев-сервер (`:3000`) |
| `pnpm lint` | ESLint |
| `pnpm typecheck` | `tsc --noEmit` |
| `pnpm test` | Vitest |
| `pnpm check` | всё сразу — **это же гоняет CI** |
| `pnpm build` | сборка Nitro в `.output/` |

Перед пушем — зелёный `pnpm check`. ⚠ **Тронули сборку — гоняйте и `pnpm build`:**
`check` его не включает, и расхождение окружений вскроется только в CI. Так и случилось
2026-09-15: `esbuild` работал локально как транзитивная зависимость и отсутствовал в CI.

## Архитектура

**Чистые ядра — в `src/domain/`, побочные эффекты — тонким слоем поверх.** Всё, что
можно проверить без сети, базы и портала, проверяется без них.

| Файл | За что отвечает | Что в нём легко сломать |
|---|---|---|
| `server/routes/b24/handler.post.ts` | приём `ONTASKADD` и `ONAPPUNINSTALL`: сверка `application_token` → очередь → **200 сразу** | любая работа до ответа. ⚠ События Б24 **не ретраятся**: медленный ответ = потерянная задача |
| `server/routes/b24/install.post.ts` | `ONAPPINSTALL` и `ONAPPUPDATE`: доказать токен вызовом `app.info` на портал **из реестра**, сохранить, подписать события | порядок проверок: в базу пишем только после доказательства. Упавший `event.bind` не должен стирать уже сохранённые токены |
| `server/routes/health.get.ts` | живость: база и Redis | Redis обязан проверяться: сервис с мёртвым Redis принимает события и молча их теряет |
| `server/plugins/bootstrap.ts` | старт: конфиг → миграции → очереди → воркеры | воркеры живут в том же процессе |
| `src/config.ts` | чтение окружения | переменная, без которой сервис **стартует, но работает неправильно** |
| `src/runtime.ts` | контекст процесса (конфиг, пул, очереди) одним синглтоном | инициализация до первого запроса; без неё роуты падают с «контекст не инициализирован» |
| `src/store/db.ts` | нумерованные миграции под advisory-lock, лок по ключу | миграции гоняются **на каждом старте**; шаги только добавляются в конец, менять применённые нельзя |
| `src/store/portalTokens.ts` | токены порталов, сверка `application_token` | токены шифруются; сверка токена — по хэшу и постоянного времени |
| `src/notify/telegram.ts` | отправка сообщений | без `parse_mode`: символы из чужого заголовка ломали бы разметку. ⚠ `TelegramHandler` из SDK эту защиту НЕ даёт — см. ниже |
| `src/domain/portals.ts` | реестр порталов из `B24_PORTAL_*` | нормализация домена: без неё событие не находит свой портал |
| `src/domain/criteria.ts` | критерии `#support` + «особый» исполнитель | срезка префикса не должна давать пустое название |
| `src/domain/taskMapping.ts` | сборка задачи для нашего портала | постановщик и исполнитель — **не** id с портала клиента |
| `src/domain/telegramMessage.ts` | тексты сообщений | сообщение об аварии без портала и id бесполезно |
| `src/crypto.ts` | AES-256-GCM для токенов, хэш `application_token` | сравнение токена — постоянного времени |
| `src/b24/eventPayload.ts` | разбор тела события | портал шлёт **форму**, а не JSON |
| `src/b24/sdk.ts` | клиенты SDK и то, чего у SDK нет: запрет редиректов, наш таймаут, перевод его ошибок в наши | ⚠ **Срок жизни токена обязан быть настоящим.** SDK сам решает, жив ли токен: при `expires` в прошлом он идёт продлевать ДО отправки запроса, а продление у нас запрещено — вызов падает «токен протух», не дойдя до портала. С `expires: 0` так упали ВСЕ вызовы на порталы клиентов на сутки (авария 2026-09-16). Закреплено тестом, который считает запросы, дошедшие до портала. ⚠ У axios внутри SDK `maxRedirects: 5` по умолчанию: без `harden` 307 увёл бы токен портала на чужой хост. ⚠ SDK заворачивает **любое** не-axios исключение из HTTP-вызова в свою ошибку с кодом `JSSDK_UNKNOWN_ERROR`, пряча исходную в `originalError`: без разворачивания терялся код `expired_token`, и продление токена не запускалось (боевой инцидент 2026-09-15). Все три поведения закреплены тестами |
| `src/b24/rest.ts` | вызовы методов — поверх `sdk.ts`; **продление токенов — отдельно, на своём `fetch`** | ⚠ Продление не переехало намеренно: у него свои требования (allow-list сервера авторизации, запрет редиректов, POST с фолбэком на GET), и они уже проверены ревью. Повтор невосстановимой ошибки прячет аварию от человека |
| `src/b24/oauthHosts.ts`, `errors.ts` | allow-list сервера авторизации; что повторять | адрес из тела запроса — это адрес, куда уедет `client_secret` |
| `src/http/readLimitedBody.ts` | потолок тела, потоком | считать байты **до** буферизации, иначе защита только на бумаге |
| `src/b24/portalClient.ts` | токены портала и их продление | ровно одна повторная попытка после продления |
| `src/b24/tasks.ts` | `tasks.task.get` / `tasks.task.add` / `user.get` | портал отдаёт id **строками** |
| `src/store/transfers.ts` | журнал переносов | дедуп держится на первичном ключе базы, а не на проверке перед вставкой |
| `src/queue/*` | BullMQ: очередь событий и очередь уведомлений | `jobId` не может содержать `:` |
| `src/pipeline/transfer.ts` | порядок переноса целиком | занять журнал **до** создания задачи |
| `src/domain/gitRepo.ts` | ссылка на репозиторий из описания группы | ⚠ Разбор строгий: две разные ссылки — отказ. Цена ошибки — issue в ЧУЖОМ приватном репозитории, а это не отзывается |
| `src/domain/issueContent.ts` | заголовок и тело issue | служебный блок с доменом и ID задачи собирается первым: при обрезке по длине режется описание, а не он. ⚠ В тело уезжает описание задачи, а в нём обратный адрес портала клиента и ФИО постановщика — осознанно: issue создаётся в репозитории того же клиента |
| `src/github/issues.ts` | создание issue | токен живёт только в заголовке запроса; за редиректами не идём |
| `src/b24/issues.ts` | группа, отбор задач, отметка, комментарий | ⚠ «Поле пустое» решает НАШ код: непонятый фильтр портал не отвергает, он возвращает всё подряд |
| `src/pipeline/exportIssues.ts` | порядок выгрузки целиком | отметка пишется **сразу после** создания issue и до комментария: сбой между ними иначе даёт второй issue |
| `src/ops/exportIssues.ts` | точка входа цели `make issues` | собирается отдельно (`pnpm build:ops`) рядом с `node_modules` образа — иначе не найдёт зависимости |

## Процесс разработки

Полностью — в [`docs/PROCESS.md`](docs/PROCESS.md). Коротко, и это правила, а не пожелания:

1. Ветка от `main`, работа в ней. **В `main` не пушим — только через PR**, даже ради
   опечатки: PR — это запись о том, почему что-то изменилось.
2. Перед панелью — влить `main` в ветку и получить зелёный `check` локально.
3. **Панель из 5 проверяющих** (инженер/корректность · QA/тесты · интеграция и
   контракты · безопасность и ПДн · тех-дир и документация) — параллельно и независимо,
   заново после каждой существенной переделки; отчёт владельцу по-русски и коротко;
   замечания устраняются **в этом же PR и до** мержа.
4. PR → зелёный CI (`ci` — required status check) → чек-лист перед мержем (свежий
   `main`, закрытые обсуждения, штампы `Last reviewed` на дату мержа) → **squash-merge**,
   ветка удаляется.
5. Деплой — автоматом с `main`, см. [`docs/DEPLOY.md`](docs/DEPLOY.md).

## Деплой

Так же, как в `client-bank-alfa-by`: образ собирается в CI, публикуется в **GHCR**, на
сервере его подхватывает **Watchtower** за общим **nginx-proxy** (TLS — Let's Encrypt).
Деплой гейтится зелёным `ci`: красная сборка не доезжает до реестра. Подробности и
переменные — [`docs/DEPLOY.md`](docs/DEPLOY.md).

**Команды на боевом сервере — только через `make`.** На сервере нет ни репозитория, ни
пакетного менеджера: только `docker-compose.prod.yml`, `Makefile` и `.env`. Любая
операция обязана быть одной вставляемой целью `make`, а не продиктованной строкой
`docker compose …`. Первой целью заводится `make self-update` — без неё остальные
бесполезны, потому что `Makefile` кладётся на сервер один раз и дальше не обновляется.

## Конвенции

- **Пользовательский текст, README и документация — на русском** (их читает владелец и
  клиент). Комментарии и JSDoc — на языке ближайшего окружения; смешение языков внутри
  одного модуля — дефект чтения.
- Чистые функции выносим отдельно и покрываем тестами; побочные эффекты (REST-вызовы,
  запись в БД) — тонким слоем поверх них.
- **По Битрикс24 не гадаем — читаем документацию.** Форма запроса, имя метода, состав
  события, название права — всё это берётся из источника, а не по памяти. Правило
  написано по конкретной цене: 2026-08-26 я послал фильтр `tasks.task.list` в форме
  старого API, получил ноль задач и записал в документацию вывод «портал не умеет искать
  по UF-полю». Неверный запрос и сломанный портал выглядят одинаково — отличает их только
  сверка с документацией. Источники, по убыванию близости к делу:

  | Что | Где смотреть |
  |---|---|
  | REST API Битрикс24 (методы, события, права) | **MCP `b24-dev-mcp`**: `bitrix-search` → `bitrix-method-details` / `bitrix-event-details` |
  | `@bitrix24/b24jssdk` | https://bitrix24.github.io/b24jssdk/llms.txt (полный срез документации одним файлом) |
  | `@bitrix24/b24ui` | https://bitrix24.github.io/b24ui/llms.txt |

  ⚠ **Документация Битрикс24 сама себе противоречит** (право `task` против `tasks` — наш
  случай). Поэтому порядок такой: документация задаёт форму запроса, живой портал
  подтверждает результат, и в документ репозитория идёт то, что подтвердилось. Один
  источник без другого уже дважды давал ложный вывод.

- **Секреты — только через окружение.** Ни токенов, ни адресов порталов в коде,
  в тестах и в логах. Персональные данные сотрудников из задач (ФИО, контакты) в
  телеметрию и спаны не кладём.
- **Учёт исходящих REST-методов Б24** ведём в [`docs/B24_EVENTS.md`](docs/B24_EVENTS.md):
  добавили метод — добавили строку. Иначе список нужных приложению прав собирается
  по коду вручную и всегда с ошибкой.
- **Штамп ревью:** каждый `.md` в корне и в `docs/` (кроме `docs/spec/` — внешний
  документ как есть) несёт строкой сразу под H1
  `> Last reviewed: YYYY-MM-DD`. Ключ на английском (технический маркер), дату бампим
  при содержательной правке. Наличие штампа проверяет `tests/mdReviewStamp.test.ts`.
- **Один факт — одно место.** Продублированные утверждения расходятся молча.
