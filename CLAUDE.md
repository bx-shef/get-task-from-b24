# CLAUDE.md

> Last reviewed: 2026-08-26

Сервис-посредник между двумя порталами Битрикс24: принимает вебхук о создании задачи
на портале-источнике и заводит задачу на портале-приёмнике.

> **Статус: каркас.** Кода нет, стек не зафиксирован; задача поставлена и описана в
> [`docs/PROCESSING.md`](docs/PROCESSING.md). Разделы с ⬜ **дозаполняются**.
>
> ⚠ **Правило этого документа: утверждаем только проверенное.** Формулировка «сделано»
> означает «прогнано вживую», а не «код написан». Для второго есть 🧪. Расхождение
> между прозой и кодом обнаруживается случайно и стоит дорого — см. легенду статусов в
> [`docs/project-map.md`](docs/project-map.md).

## Стек

Зафиксирован владельцем 2026-08-26 — тот же, что в `client-bank-alfa-by`, минус фронтенд
(интерфейса у сервиса нет):

| Что | Чем | Почему именно так |
|---|---|---|
| рантайм | **Node 22 LTS** + **pnpm** (через corepack, версия в `packageManager`) | как в соседнем проекте: одни привычки, один деплой |
| сервер | **Nitro** (без Nuxt) | нужны только HTTP-роуты; фронтенд-фреймворк здесь лишний слой |
| база | **Postgres** | токены порталов продлеваются в рантайме, журнал переносов обязан переживать перезапуск |
| очередь | **Redis + BullMQ** | события Б24 **не ретраятся** — приём и обработка обязаны разъехаться |
| тесты | **Vitest** | |
| линт | **ESLint** | |

⚠ **Очередь здесь не «для масштаба», а по существу задачи.** Обработчик обязан ответить
200 до всякой работы, иначе задача клиента теряется молча и навсегда.

## Команды

⬜ **Дозаполняется вместе со стеком.** Обязательный минимум, который гоняет CI и который
автор гоняет перед пушем, — одна команда `check` = линт + типы + тесты.

| Команда | Что делает |
|---|---|
| `<pkg> dev` | дев-сервер |
| `<pkg> lint` | линтер |
| `<pkg> typecheck` | проверка типов |
| `<pkg> test` | тесты |
| `<pkg> check` | всё сразу — **это же гоняет CI** |

## Архитектура

⬜ **Карта модулей дозаполняется по мере появления кода** (файл — за что отвечает — что
в нём легко сломать). Контур задачи зафиксирован:

- **Приём события** — `POST /b24/handler`. Проверяет `application_token`, кладёт событие
  в очередь и **отвечает 200 сразу**. ⚠ События Б24 **не ретраятся**: медленный или
  упавший ответ = задача потеряна навсегда и молча.
- **Установка** — `POST /b24/install` (`ONAPPINSTALL`). Вызывается **один раз** при
  сохранении формы локального приложения у клиента; здесь сохраняются токены портала
  и `application_token`, здесь же делается `event.bind` на `onTaskAdd`.
- **Реестр порталов** — 20–30 клиентов: домен, id «особого» исполнителя,
  `client_id`/`client_secret` (окружение) + живые OAuth-токены (перечитываемое
  хранилище: они продлеваются в рантайме, окружение — нет).
- **Очередь** — вычитать задачу (`tasks.task.get` у клиента), проверить критерии,
  дедуп по журналу, создать (`tasks.task.add` у нас), уведомить Telegram. Ретраи —
  на каждом внешнем вызове.
- **Журнал переносов** — `портал + ID задачи-источника → ID задачи у нас`. Без него
  повторная доставка события заводит дубль, и заметит это человек, а не тест.
- **Telegram** — отдельным шагом: упавшее сообщение не должно приводить к повторному
  созданию задачи.

Спецификация — [`docs/PROCESSING.md`](docs/PROCESSING.md), контракт событий и методов —
[`docs/B24_EVENTS.md`](docs/B24_EVENTS.md), сторона клиента —
[`docs/CLIENT_APP.md`](docs/CLIENT_APP.md).

## Процесс разработки

Полностью — в [`docs/PROCESS.md`](docs/PROCESS.md). Коротко, и это правила, а не пожелания:

1. Ветка от `main`, работа в ней. **В `main` не пушим — только через PR.**
2. Перед PR — зелёный `check` локально.
3. **Панель из 5 проверяющих** (корректность · тесты · интеграция/контракты ·
   безопасность/ПДн · тех-дир), замечания устраняются **до** мержа.
4. PR → зелёный CI (`ci` — required status check) → **squash-merge**, ветка удаляется.
5. Деплой — автоматом с `main`, см. [`docs/DEPLOY.md`](docs/DEPLOY.md).

## Деплой

Так же, как в `client-bank-alfa-by`: образ собирается в CI, публикуется в **GHCR**, на
сервере его подхватывает **Watchtower** за общим **nginx-proxy** (TLS — Let's Encrypt).
Деплой гейтится зелёным `ci`: красная сборка не доезжает до реестра. Подробности и
переменные — [`docs/DEPLOY.md`](docs/DEPLOY.md).

**Команды на боевом сервере — только через `make`.** На сервере нет ни репозитория, ни
пакетного менеджера: только `docker-compose.prod.yml`, `Makefile` и `.env`. Любая
операция обязана быть одной вставляемой целью `make`, а не продиктованной строкой
`docker compose …`. Первой целью заводится `make self-update` — без неё остальные
бесполезны, потому что `Makefile` кладётся на сервер один раз и дальше не обновляется.

## Конвенции

- **Пользовательский текст, README и документация — на русском** (их читает владелец и
  клиент). Комментарии и JSDoc — на языке ближайшего окружения; смешение языков внутри
  одного модуля — дефект чтения.
- Чистые функции выносим отдельно и покрываем тестами; побочные эффекты (REST-вызовы,
  запись в БД) — тонким слоем поверх них.
- **Секреты — только через окружение.** Ни токенов, ни адресов порталов в коде,
  в тестах и в логах. Персональные данные сотрудников из задач (ФИО, контакты) в
  телеметрию и спаны не кладём.
- **Учёт исходящих REST-методов Б24** ведём в [`docs/B24_EVENTS.md`](docs/B24_EVENTS.md):
  добавили метод — добавили строку. Иначе список нужных приложению прав собирается
  по коду вручную и всегда с ошибкой.
- **Штамп ревью:** каждый `.md` в корне и в `docs/` несёт строкой сразу под H1
  `> Last reviewed: YYYY-MM-DD`. Ключ на английском (технический маркер), дату бампим
  при содержательной правке. Когда появятся тесты — наличие штампа закрепляем тестом.
- **Один факт — одно место.** Продублированные утверждения расходятся молча.
