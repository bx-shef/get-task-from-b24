# get-task-from-b24

> Last reviewed: 2026-09-16

Сервис-посредник: обращение клиента из его Битрикс24 становится задачей в нашем
Битрикс24 и issue в его репозитории на GitHub.

## Цели

- **Одно обращение = одна задача = один issue.** Клиент пишет у себя, мы работаем
  у себя, код живёт на GitHub — и всё это одна сущность, а не три разных.
- **Ничего не теряется.** События Битрикс24 приходят один раз и не повторяются,
  поэтому приём и обработка разделены очередью.
- **Ничего не задваивается.** Повторное событие, ручной досыл и гонка двух
  обработчиков не должны давать вторую задачу или второй issue.
- **20–30 клиентов на одного человека.** Всё, что делается руками на каждом клиенте,
  рано или поздно станет узким местом — поэтому подключение и эксплуатация идут
  готовыми командами.

## Структура

```
Портал клиента ──событие──▶ сервис ──▶ очередь ──▶ наш Битрикс24
                                          │
                                          ├──▶ Telegram (сигнал человеку)
                                          └──▶ GitHub: issue в репозитории клиента
```

| Часть | Что делает |
|---|---|
| Порталы клиентов (2 подключено) | локальное приложение «только API», шлёт нам событие о созданной задаче |
| Сервис | принимает событие, проверяет критерии, заводит задачу у нас, выгружает в issue |
| Наш Битрикс24 | где мы работаем; связка с задачей клиента лежит в полях самой задачи |
| GitHub | приватный репозиторий клиента, туда уезжают issue |

Устройство кода и правила разработки — [`CLAUDE.md`](CLAUDE.md).

## Процесс

**Как проходит обращение:**

1. Клиент создаёт задачу с префиксом `#support` на «особого» исполнителя.
2. Его портал шлёт нам событие — в нём только ID задачи.
3. Отвечаем 200 сразу и кладём событие в очередь.
4. Читаем задачу у клиента, проверяем критерии. Не подошла — в лог, это норма.
5. Спрашиваем свой портал: не переносили ли уже. Переносили — останавливаемся.
6. Заводим задачу у себя, сверяем, что не создалось две, шлём сигнал в Telegram.
7. По команде выгружаем задачи в issue репозитория клиента.

**Как делается правка:**

ветка от `main` → код + тесты + документация одним PR → панель из 5 проверяющих
в два круга → зелёный CI → squash-мерж → выкат автоматом → **живая проверка на портале**.

Последний шаг обязателен: пока его не было, статус 🧪, а не «сделано». Подробно —
[`docs/PROCESS.md`](docs/PROCESS.md).

## Что дальше

| Что | Зачем именно это |
|---|---|
| Кнопка «Отправить в sh-support-bx» в карточке задачи | ручной путь, когда сервис не работал и событие не пришло вовсе. Требует нового права у приложения, то есть обновления у каждого клиента, — чем позже, тем дороже |
| Прототипы механик переписки и GitHub App | схема переписки не окончательная, а на ней стоит весь следующий этап |
| Реестр клиентов в смарт-процессах | сейчас клиенты живут строками в окружении сервера; на 20–30 порталов так не масштабируется |
| Форма тикета вместо префикса `#support` | префикс — заглушка: поля должны приходить формой, а не угадываться из чужой задачи |
| GitHub-контур целиком | статусы клиенту меняются от событий GitHub без ручного участия. Главный технический риск этапа |

Этапы и критерии приёмки — [`docs/ROADMAP.md`](docs/ROADMAP.md), продукт целиком —
[`docs/PRODUCT.md`](docs/PRODUCT.md).

## Команды

Разработка: `pnpm install` → `pnpm dev` → `pnpm check` (то же гоняет CI).

На сервере — только через `make`: `make self-update` (первой после обновления),
`make doctor`, `make logs-tail`, `make queue`, `make backfill`, `make issues`.
Выкат и эксплуатация — [`docs/DEPLOY.md`](docs/DEPLOY.md).
