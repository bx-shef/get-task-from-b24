# Локальное приложение на портале клиента

> Last reviewed: 2026-08-26

Как клиент подключает свой Битрикс24 к нашему обработчику. Порталов планируется
**20–30**, поэтому процедура обязана быть короткой и одинаковой для всех.

Факты ниже — из официальной документации
([локальное приложение без интерфейса](https://apidocs.bitrix24.ru/local-integrations/serverside-local-app-with-no-ui.html),
[`ONTASKADD`](https://apidocs.bitrix24.ru/api-reference/tasks/events-tasks/on-task-add.html)).

## Что заводит клиент

**Приложения → Разработчикам → Другое → Локальное приложение.**

| Поле формы | Значение |
|---|---|
| **Приложение использует только API** | ☑ включить — интерфейса у нас нет |
| **Путь вашего обработчика** | `https://<наш-домен>/b24/handler` (только HTTPS) |
| **Путь для первоначальной установки** | `https://<наш-домен>/b24/install` |
| **Права (scope)** | «Задачи» + «Пользователи (базовый)» |

После сохранения форма показывает **код приложения** (`client_id`) и **секретный ключ**
(`client_secret`) — их клиент передаёт нам.

⚠ **Права на пользователей нужны только ради имени постановщика** в описании
переносимой задачи, и просим мы самый узкий вариант (`user_brief` — ФИО без остальных
персональных данных). Не дали — перенос всё равно работает, в описании будет «id 3»
вместо «Иван Петров»: `fetchUserName` глотает отказ намеренно, ронять задачу из-за
красивого текста нельзя.

✅ **Замерено на живом портале 2026-08-26: право называется `task`.** `tasks.task.get`
отработал без отказа по правам. Документация Битрикс24 противоречит сама себе (страница
события `OnTaskAdd` объявляет `task`, страницы `tasks.task.*` — `tasks`), поэтому это
именно замер, а не вычитанный факт.

⚠ **Обработчик обязан быть доступен по HTTPS ДО добавления приложения** — иначе Битрикс24
не сохранит форму.

⚠ **«Путь для первоначальной установки» вызывается ровно один раз** — это обработчик
события `ONAPPINSTALL`, и именно в нём мы сохраняем токены портала (включая
`application_token`, которым потом проверяется подлинность событий). Пропустили этот
вызов — приложение стоит, а работать не может, и переустановка потребует участия клиента.

⚠ **События не отправляются, пока установка не завершена.** Приложение, у которого
установка не финализирована, не получит ни одного `ONTASKADD` — и это выглядит как
«ничего не приходит», а не как ошибка.

## Подписка на событие

После установки подписываемся сами:

```
event.bind(event: "onTaskAdd", handler: "https://<наш-домен>/b24/handler")
```

Проверять подписку нужно **идемпотентно** (повторная установка не должна плодить
обработчиков) и уметь пересоздавать её, если клиент чистил интеграции.

## Наш Битрикс24 (портал-приёмник)

Подключается **входящим вебхуком** — приложение там не нужно: мы только пишем.
Права вебхука: `task`. URL вебхука — секрет, живёт в окружении и в логи не попадает.

⚠ Входящий вебхук привязан к конкретному сотруднику: задачи будут создаваться от его
имени, и его увольнение/смена прав ломает перенос молча.

## ⚠ Масштаб: 20–30 порталов — это 20–30 приложений

Локальное приложение создаётся **на каждом портале отдельно**, со своей парой
`client_id`/`client_secret` и своими токенами. Это не деталь оформления, а решение
об архитектуре хранения:

**Решено:** секреты — в окружении, живые токены — в Postgres.

| Вариант | За | Против |
|---|---|---|
| всё в переменных окружения | нет БД, деплой простой | токены продлеваются в рантайме, а окружение не меняется — продление некуда записать |
| **секреты в окружении, токены в БД** ← выбрано | токены продлеваются штатно и переживают перезапуск | нужна БД (она всё равно нужна под журнал переносов) |
| всё в БД, окружение только для доступа к ней | добавление портала без передеплоя | нужен способ завести портал — команда или админка |

Формат реестра — по одной переменной на портал; он описан в `.env.example`, здесь не
дублируем. Правится целями `make client-add` / `client-disable`
([`DEPLOY.md`](DEPLOY.md)), а не руками.

⚠ **Ни JSON, ни `|` — оба ломаются молча, замерено живым прогоном.** JSON-массив одной
переменной разваливается о `source .env` (шелл съедает кавычки), разделитель `|` там же
превращается в конвейер («17: command not found»). Запятая проходит и через шелл, и
через `env_file` docker compose. Отдельная переменная на портал ещё и правится по одной —
в том числе с телефона, а не «весь список целиком и вслепую».

⚠ **Токены OAuth протухают и продлеваются в рантайме** (`refresh_token`). Переменные
окружения при этом не меняются — значит хранить в них можно только то, что не меняется:
домен, id ответственного, `client_id`/`client_secret`. Живые токены нужно писать туда,
откуда их можно перечитать после перезапуска.



## Что мы просим у клиента (памятка)

1. Домен портала.
2. `client_id` и `client_secret` заведённого локального приложения.
3. **Id «особого» ответственного** — по нему отбираются задачи на перенос
   (`user.get` в портале, либо ссылка на профиль сотрудника: id виден в адресе).

Со своей стороны заводим строку в реестре (`make client-add`) и, если нужно, указываем
группу нашего портала, куда пойдут задачи этого клиента.
