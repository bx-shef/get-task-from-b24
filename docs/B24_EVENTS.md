# События и REST-методы Битрикс24

> Last reviewed: 2026-08-26

Контракт с двумя порталами: что нам **приходит** от портала-источника и что мы
**вызываем** на портале-приёмнике. Факты ниже взяты из официальной документации
(apidocs.bitrix24.ru), а не выведены; помеченное ⬜ — решение постановки, его ещё нет.

## Входящее событие: `ONTASKADD`

Скоуп `task`, подписка — `event.bind`. Приходит **POST**-запросом на наш обработчик.

```json
{
  "event": "ONTASKADD",
  "data": {
    "FIELDS_BEFORE": { "ID": 123 },
    "FIELDS_AFTER":  { "ID": 123 },
    "IS_ACCESSIBLE_BEFORE": "N",
    "IS_ACCESSIBLE_AFTER":  "undefined"
  },
  "ts": "1466439714",
  "auth": { "domain": "…", "member_id": "…", "application_token": "…", "access_token": "…", "…": "…" }
}
```

⚠ **В событии приходит ТОЛЬКО `ID` задачи, а не её поля.** `FIELDS_AFTER` содержит
единственный ключ `ID`; ни названия, ни исполнителя, ни сроков там нет. Значит перенос
физически невозможен без второго шага — вычитать задачу методом `tasks.task.get` на
портале-источнике. Это определяет архитектуру: обработчик события и сборщик данных —
разные шаги, и второй ходит в портал по токену, а не по содержимому запроса.

⚠ **`auth` приходит не всегда.** Если хит, породивший событие, не привязан к конкретному
пользователю портала, токены в событии отсутствуют. Полагаться на `auth.access_token` из
тела нельзя — нужны свои сохранённые токены портала. Содержимое `auth` проверяем в коде
явно.

⚠ **`application_token` — единственное, что отличает событие портала от подделки.**
Наш эндпоинт открыт миру: сверяем токен с сохранённым при установке **до** любой работы.

⚠ **События не ретраятся.** Пропущенное или отвергнутое ошибкой событие потеряно
навсегда — задача просто не приедет, и молча. Отсюда правило: обработчик отвечает
быстро и успешно, а вся работа уходит в очередь/журнал.

⚠ **До завершения установки приложения события не отправляются** — если на портале
установка не финализирована, обработчик не позовут ни разу.

⬜ **Дозаполняется:** подписываемся ли также на `ONTASKUPDATE` / `ONTASKDELETE`
(см. [`IDEAS.md`](IDEAS.md) — синхронизация после переноса вынесена «на потом»).

## Исходящие методы REST

Учёт ведём здесь: добавили вызов — добавили строку. Иначе список нужных приложению
скоупов собирается по коду вручную и всегда с ошибкой.

| Метод | Скоуп | Портал | Где вызывается | Зачем |
|---|---|---|---|---|
| `event.bind` | `task` | источник | ⬜ | подписка на `ONTASKADD` |
| `tasks.task.get` | `task` | источник | ⬜ | вычитать поля задачи по `ID` из события |
| `tasks.task.add` | `task` | приёмник | ⬜ | создать задачу-копию |

⬜ **Дозаполняется:** сопоставление пользователей (`user.get`), проектов/групп,
чек-листов и вложений — по мере постановки.

## Аутентификация двух порталов

| Портал | Роль | ⬜ Способ доступа |
|---|---|---|
| источник | шлёт нам событие, отдаёт поля задачи | тиражное приложение (OAuth) или входящий вебхук — решается постановкой |
| приёмник | принимает создание задачи | то же |

⚠ Токены и адреса порталов — только в окружении/шифрованном хранилище, никогда в коде,
в тестах и в логах. `member_id` пригоден как идентификатор портала в журналах;
`access_token` и `application_token` — нет.

## Дедупликация

Журнал `member_id источника + ID задачи-источника → ID задачи-приёмника`, запись —
до или одновременно с созданием. Повторная доставка события (а она возможна) не должна
заводить вторую задачу; без журнала это заметит человек, а не тест.
