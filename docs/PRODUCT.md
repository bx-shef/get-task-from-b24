# Что мы строим

> Last reviewed: 2026-08-27

Описание продукта целиком: зачем он, из чего состоит и где в нём находится то, что
уже работает. Разбивка на этапы — [`ROADMAP.md`](ROADMAP.md), текущее состояние —
[`project-map.md`](project-map.md).

Источник требований — пакет документации, переданный владельцем 2026-08-27 и
положенный в [`spec/`](spec/) как есть. Здесь он не пересказывается: этот документ
объясняет, **как спецификация ложится на то, что у нас уже построено**, и где она с
реальностью расходится.

## Продукт одной фразой

**Система работы с обращениями:** клиент пишет обращение у себя в Битрикс24, оно
превращается в задачу у нас и в issue на GitHub, проходит цикл разработки, а по итогам
месяца клиенту выставляется счёт.

```
Портал клиента          наш Битрикс24              GitHub
──────────────          ─────────────              ──────
форма тикета  ────────▶ задача (тикет)  ────────▶  issue
переписка     ◀───────▶ чат задачи      ◀───────▶  комментарии
статус        ◀──────── контроль        ◀────────  PR, Actions
счёт          ◀──────── инвойс + акт
```

**Кто платит за что.** Приложение в маркетплейсе бесплатное; доход — договор поддержки.
Отсюда следствие, зашитое в архитектуру: всё вендорское (портал оператора, ID
смарт-процессов, GitHub App, AI-endpoint) — конфигурация, а не хардкод, чтобы систему
можно было продать другой студии.

## Три сущности, на которых всё держится

**Клиент → проект → тикет.** Клиент — это портал и организация. Проект — это договор
плюс репозиторий; у клиента их может быть несколько. Тикет всегда привязан к проекту, и
через проект однозначно резолвятся и репозиторий для issue, и тариф для счёта.

⚠ **Единица биллинга — проект, а не клиент.** У клиента с двумя проектами два
независимых счёта, каждый по своему тарифу и в свой расчётный день.

**Инвариант: 1 тикет = 1 задача = 1 issue.** Новые issue внутри старого тикета не
создаются никогда; если работа не принята — это новый тикет с ссылкой на родителя.

## Где в этой картине то, что уже работает

Наш сервис — **транспорт из левой колонки в среднюю**, и он в бою: событие с портала
клиента доезжает до задачи в нашем Битрикс24. Это меньше, чем весь продукт, но это
несущая конструкция, и она проверена не рассуждением.

| Что построено | Как переиспользуется дальше |
|---|---|
| приём событий портала: ответ 200 до работы, сверка `application_token`, потолок тела | без изменений — это вход для любого события клиента |
| очередь BullMQ с ретраями и политикой невосстановимых ошибок | без изменений — на неё лягут GitHub и AI |
| хранение токенов порталов: шифрование, продление под advisory-lock | без изменений — токенов станет 20–30 вместо одного |
| журнал переносов с дедупом на первичном ключе | ⚠ **убирается** — связка ищется по UF-полям задачи (см. расхождение 1а) |
| реестр клиентов в окружении + цели `make` | переезжает в смарт-процессы «Клиенты» и «Проекты» |
| деплой, CI, `Makefile`, смоук, панель ревью | без изменений |
| Telegram-алерты | становятся алертами в чат Б24 (решение Б4), Telegram остаётся запасным |

**Что придётся заменить:** триггер. Сейчас тикетом становится задача с префиксом
`#support` на «особом» исполнителе — это заглушка вместо формы. В целевой системе
клиент нажимает «Создать обращение» в приложении, и поля приходят формой, а не
угадываются из чужой задачи.

## Расхождения спецификации с замеренной реальностью

Три места, где спецификация расходилась с нашей реальностью. Все три закрыты решениями
владельца 2026-08-27; ниже — что решено и почему это было развилкой.

### 1. Решение Б2 «собственной СУБД нет» — принято и **замерено**

**Решение владельца 2026-08-27: связка живёт в UF-полях, отдельная база под неё не
нужна.** Обоснование владельца: своя СУБД понадобилась бы ради маркетплейса, а туда мы
не собираемся.

✅ **Замер на боевом портале 2026-08-27** (задача 1517, 565 задач видно вебхуку; проверялись
семь форм запроса разовым скриптом):

| Форма запроса | Результат |
|---|---|
| `filter[UF_SOURCE_TASK_ID]=120005` (объектом) | **нашёл ровно её**, `total 1` |
| `filter[0][0]=поле, filter[0][1]=значение` (массивом) | 400, `Invalid filter value: 'UF_SOURCE_TASK_ID'` |
| то же в теле JSON — числом, строкой, с оператором `=` | 400, то же |
| то же в camelCase | 400, `Invalid filter value: 'ufSourceTaskId'` |

⚠ **Значение из поля приходит строкой** (`"120005"`), хотя само поле числовое (`double`).
Сравнивать при поиске — как строку.

**Вывод, ровно в границах замеренного: `tasks.task.list` на нашем боевом портале находит
задачу по UF-полю, если фильтр послан объектом.** Про другие методы, другие порталы и
другие формы это не говорит ничего. Для нашей задачи достаточно: связка тикет↔issue в
UF-полях — рабочий механизм, и отдельный индекс под неё не нужен.

⚠ **Дважды подряд я ошибся на этом месте, и оба раза одинаково — обобщал за пределами
замеренного.** Сначала записал «портал не умеет искать по UF-полю», хотя мерил один
запрос. Потом, прочитав в документации REST v3 форму `filter` массивом, записал, что
объектная форма устарела, — а портал принимает именно её и отвергает «правильную».
Почему тот же запрос 2026-08-26 вернул ноль — **не установлено**; сегодняшний замер
воспроизводим, вчерашний нет. Правило, которое из этого следует, уже записано в
[`../CLAUDE.md`](../CLAUDE.md): документация задаёт форму запроса, живой портал
подтверждает результат, и в документ идёт то, что **подтвердилось**.

### 1а. Журнал переносов заменяется поиском по порталу

**Решение владельца 2026-08-27:** журнал `transfers` убрать; переносилась ли задача —
спрашивать у нашего Битрикс24 по паре `UF_SOURCE_TASK_ID` + `UF_SOURCE_DOMAIN`. Это стало
возможным ровно после замера выше: раньше связку негде было спросить, теперь есть где.

Журнал делает четыре работы, и у каждой свой ответ:

| Что делает журнал сейчас | Чем заменяется |
|---|---|
| **1. Сопоставление** «задача клиента → наша задача» | поиском по паре UF-полей — замерено, работает |
| **2. Держит место** до создания задачи: строка занимается **до** `tasks.task.add` | сверкой **после** создания — см. ниже |
| **3. Хранит причину отказа**, переживает перезапуск | ничем: хранилище отказов не заводится (решение владельца) |
| **4. Даёт оператору `make transfers`** | целью, которая смотрит очередь и логи |

**По пункту 2 — гонка закрывается постфактум, и это надо называть своим именем.** `jobId`
очереди (пара «домен + задача») существовал одновременно с журналом и не покрывает случай,
ради которого держали блокировку: BullMQ возвращает зависшее задание после падения воркера,
и это то же задание с тем же `jobId`, а не второе событие. Значит превентивной защиты не
остаётся, и заменяет её сверка после создания: создали → спросили портал по ключу → если
задач больше одной, созданная позже удаляется, в Телеграм уходит сигнал. Это и есть
«ротировать и удалять, если что-то не так» из постановки.

**По пунктам 3 и 4 — решение владельца 2026-08-27: хранилища отказов не будет.** Логика
такая: очередь и есть механизм надёжности. Не работает обработчик — чиним обработчик, и он
разгребает очередь; строка в базе тут ничего не добавляет, кроме второго места, за которым
надо следить.

⚠ **Из этого следует одна вещь, которую надо принять сознательно.** Если Redis недоступен в
момент события, положить в очередь нечего и событие потеряно — второй доставки у Битрикс24
нет. Сегодня на этот случай пишется строка в журнал; после снятия таблицы остаётся сигнал в
Телеграм и запись в лог, то есть человек узнаёт, но автоматического восстановления нет. Это
тот же класс отказа, что и «сервис лежит целиком»: там событие вообще не доходит. У обоих
один ответ — кнопка ниже.

### 1б. Кнопка «Отправить в sh-support-bx» в карточке задачи

**Решение владельца 2026-08-27.** Если сервис не работал в момент создания задачи, событие
не придёт никогда. Значит нужен ручной путь: человек открывает задачу на портале клиента и
отправляет её нам кнопкой.

Из документации Битрикс24 (сверено, не по памяти):

- **Точка встраивания** — `TASK_VIEW_TAB` (либо `TASK_VIEW_SIDEBAR` / `TASK_VIEW_TOP_PANEL`).
  В новой карточке задач (модуль `tasks` 25.700.0+) отдельной вкладки нет: все три точки
  выводятся строками в блоке «Приложения» под полями задачи.
- **Регистрируется** методом `placement.bind` с `PLACEMENT`, `HANDLER`, `TITLE`; параметр
  `OPTIONS.groupId` умеет ограничить вывод задачами конкретных проектов.
- **Обработчик получает** POST: `DOMAIN`, `member_id`, `APPLICATION_TOKEN`, `AUTH_ID` и
  `PLACEMENT_OPTIONS` — JSON-строкой, в ней `taskId`. То есть ровно то, что нужно: домен и
  id задачи. `APPLICATION_TOKEN` — тот же, что в событиях, значит подлинность запроса
  проверяется уже написанным кодом.
- **Ответ обработчика** — HTML-страница: Битрикс24 показывает её во фрейме на месте
  виджета. Страница обязана разрешать встраивание — заголовки `X-Frame-Options` и
  `Content-Security-Policy`, запрещающие фрейм, дают пустую область вместо виджета.

⚠ **Цена, которую видно заранее.** Точка требует скоупа `placement` вдобавок к `task`, а
наше приложение у клиентов — «только API», без интерфейса. Значит: каждому клиенту придётся
**обновить приложение** (изменение состава прав), и у сервиса впервые появляется страница,
которую отдают в браузер. Пока клиент один — это дёшево; чем позже, тем дороже, поэтому
делать стоит до подключения остальных.

**Что делает кнопка:** берёт `taskId` и `DOMAIN`, проверяет `APPLICATION_TOKEN`, кладёт
событие в ту же очередь, что и вебхук, и отвечает страницей «поставлено в очередь». Критерии
переноса при этом не обходятся: задача без `#support` или с чужим исполнителем так же не
переносится — кнопка чинит доставку события, а не правила отбора.

### 2. Домен попадает к клиентам и потом не меняется

Спецификация называет `support.bx-shef.by`, у нас работает
`get-task-from-b24.bx-shef.by`. Это не косметика: адрес обработчика вписывается в форму
приложения **у каждого клиента**, и смена адреса потребует участия каждого из них. Мы
это уже проходили, когда заводили первый портал.

**Решено 2026-08-27: остаётся `get-task-from-b24.bx-shef.by`.** Спецификационный
`support.bx-shef.by` не используем — переезд стоил бы участия каждого подключённого
клиента, а выгоды не даёт никакой.

### 3. Локальные приложения против одного маркетплейсного

Сейчас у каждого клиента своё **локальное** приложение со своей парой
`client_id`/`client_secret` — 20–30 приложений, и каждое клиент заводит руками.
Спецификация предполагает **одно** приложение из маркетплейса: один `client_id` на всех,
установка в один клик.

**Решено 2026-08-27: в маркетплейс не скоро.** Значит локальные приложения — рабочий и
единственный путь, и проектировать под маркетплейс сейчас не нужно. Цена известна и
принята: онбординг каждого клиента включает ручное заведение приложения.

## Что наш прогон уже дал спецификации

Пять фактов, снятых на живых порталах. Они не переспорены документацией — они её
дополняют, и все пять уже влияют на код.

| Факт | Следствие для системы |
|---|---|
| в `ONTASKADD` приходит **только ID** задачи | любой поток от события требует второго похода в портал; критерии проверяются после него |
| события Б24 **не ретраятся** | обработчик обязан отвечать 200 до всякой работы; вся работа — из очереди |
| поиск по UF-полю **работает**, фильтр — объектной формой | связка тикет↔issue живёт в полях задачи; журнал переносов не нужен (см. расхождение 1) |
| удалённая задача приходит **пустым списком**, а не ошибкой | иначе человек читает про формат ответа вместо «задачу удалили» |
| право на задачи называется **`task`** | документация Битрикс24 противоречит сама себе (`task` против `tasks`); замерено на живом портале |

## Что решено и что осталось

Развилки закрыты владельцем 2026-08-27: домен остаётся текущий, связка живёт в UF-полях
(замерено), журнал переносов убирается, маркетплейс — не скоро. Открытым остаётся
немногое:

- **Замена журнала переносов** поиском по порталу и **кнопка в карточке задачи** — решено,
  делается кодом после переезда на SDK (см. 1а и 1б).
- **Префикс `#support`** — общий на всех клиентов или свой у каждого. Вопрос живёт
  ровно до появления формы тикета: с ней префикс исчезает как понятие.
