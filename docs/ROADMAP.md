# Этапы: цель, выгоды, критерии приёмки

> Last reviewed: 2026-08-27

Разбивка продукта из [`PRODUCT.md`](PRODUCT.md) на этапы. Нумерация этапов — из
спецификации ([`spec/spec-ticketing.md`](spec/spec-ticketing.md), решения Б10 и А11):
1 — пилот, 2 — биллинг, 3 — AI, 4 — маркетплейс. Добавлен **этап 0**: то, что уже
работает в бою; спецификация его не выделяла, потому что писалась до него.

Текущее положение внутри этапов — [`project-map.md`](project-map.md). Здесь только
**зачем этап нужен и по чему считать его законченным**.

⚠ **Критерий приёмки — это то, что можно предъявить.** «Реализовано», «покрыто
тестами» и «работает» — три разных утверждения (легенда ✅/🧪 в
[`project-map.md`](project-map.md)). Критерии ниже сформулированы как прогон на живом
портале, потому что дважды за этот проект зелёные тесты расходились с боем.

⚠ **Значки статуса в критериях не ставим.** Критерий — это обещание, а ✅ в этом репо
означает «проверено вживую»; ✅ на невыполненном критерии через полгода читается как
факт. Единственное исключение — этап 0: там критерии действительно закрыты, и рядом
стоит дата прогона.

документ отвечает на вопрос «по чему считать этап законченным», а не «где мы сейчас».

Этапы 2 и 3 независимы друг от друга и оба зависят от 1. Этап 4 можно начинать
параллельно с 2, но нельзя раньше конца пилота: в маркетплейс подаётся то, что уже
прошло живую эксплуатацию (решение Б7 — демо-режима нет, модератор идёт по настоящему
потоку).

  [`PRODUCT.md`](PRODUCT.md)); два из них меняют её решения.

**Критерии приёмки — все выполнены 2026-08-26:**

- ✅ Задача `#support` с портала клиента доехала целиком: `120005 → 1517`, журнал
  `done`, уведомление пришло.
- ✅ Сервис развёрнут на боевом домене, TLS выпущен, деплой автоматический с `main`.
- ✅ Обработчик отвечает 200 до всякой работы; событие обрабатывается из очереди.
- ✅ Повторная доставка события не создаёт вторую задачу (дедуп на первичном ключе).
- ✅ Токены портала хранятся зашифрованными и продлеваются в рантайме.

## Этап 1. Пилот: контур тикетов

Разделы 1–6 спецификации без биллинга и AI. Три клиента, по одному проекту (решение
Б10): двое по факту часов, третий по согласованным оценкам — поэтому стадия «Оценка»
входит в этот этап, а не откладывается до биллинга.

**Цель.** Клиент создаёт обращение у себя в Битрикс24 в форме, а не письмом; обращение
проходит полный цикл — задача, issue, ветка, PR, тесты, контроль — и клиент видит статус
и итог, ни разу не спросив «а что там с моей заявкой».

**Выгоды.**

- **Владельцу:** одна очередь работ вместо трёх каналов; видно, кто чем занят и сколько
  висит непринятого; часы фиксируются по ходу дела, а не восстанавливаются в конце
  месяца по памяти (это же входные данные для этапа 2).
- **Клиенту:** заявка не теряется, статус виден без вопросов, вся переписка по обращению
  в одном месте.
- **Проекту:** после этого этапа система в принципе работает — дальше идут контуры,
  каждый из которых можно не делать и жить.

**Критерии приёмки:**

- Сквозной сценарий прогнан **на каждом из трёх пилотных проектов**: форма → задача +
  issue → ветка → PR → мердж → зелёные Actions → контроль → «Решён» у клиента.
- Клиент №3 прошёл стадию «Оценка»: подтвердил оценку, issue создан только после
  подтверждения; отдельно проверен отказ → статус «Отменён», issue не создан.
- Переписка ходит в обе стороны: сообщение из чата задачи доехало клиенту и в issue,
  комментарий клиента — в чат задачи с пометкой «от клиента».
- Возврат проверен вживую в двух вариантах: красные Actions и «контроль не принял» —
  задача вернулась в работу, **новый issue не создан**.
- Негативный отзыв создал **новый тикет** со ссылкой на родителя и своим issue.
- Пилот прожил 2–4 недели живой работы, и за это время ни одно обращение не потерялось
  и не задвоилось.
- Почасовая сверка не находит расхождений: задач без issue, issue без задач и закрытых
  тикетов без часов нет.
- Порталы без активного договора видят экран «свяжитесь с нами», а не форму.
- Правило [`../CLAUDE.md`](../CLAUDE.md) «ПДн в телеметрию не кладём» держится не на
  словах: в логах бэкенда за сутки пилота нет ни ФИО и контактов из карточек клиентов,
  ни содержимого тикетов — проверено грепом. Грep здесь подтверждает конструкцию, а не
  заменяет её: если ПДн нашлись, чинится место, где они пишутся, а не журнал.

### Инкременты

Порядок — по риску, а не по слоям: сначала то, что может обрушить схему, потом то, что
можно доделывать при живом пилоте. Каждый инкремент — слайс по
[`PROCESS.md`](PROCESS.md): код + тесты + документация в одном PR.

| # | Инкремент | Что снимает | Готово, когда |
|---|---|---|---|
| **1.0** | Прототипы механик: пункт меню сообщения в чате задачи (в том числе в мобильном), канал входящих комментариев, GitHub App и его вебхуки | риск переделки схемы переписки | пункт виден в чате задачи, handler получает данные сообщения; issue создаётся, `issues`/`pull_request`/`workflow_run` доходят |
| **1.1** | Реестр: смарт-процессы «Клиенты» и «Проекты», перенос туда реестра из окружения | env перестаёт быть базой данных | скрипт заводит оба смарт-процесса воспроизводимо; клиент и проект резолвятся по порталу |
| **1.2** | Форма тикета вместо префикса `#support`; создание задачи с контролёром и флагом «принять работу» | заглушку-триггер | тикет из формы создаёт задачу с правильным постановщиком; повтор формы не задваивает |
| **1.3** | GitHub-контур: issue по тикету, ветка `ticket/{id}`, `Closes #N`, маппинг статусов по разделу 4 | главный технический риск этапа | статус клиенту меняется от событий GitHub без ручного вмешательства |
| **1.4** | Переписка и возвраты: лента в карточке, «Отправить клиенту» / «Отправить в issue», правила 1–3 | | все три правила возврата прогнаны вживую |
| **1.5** | Стадия «Оценка», порог из договора, мобильная вёрстка, запрет закрытия оплачиваемого тикета с нулевым временем | | клиент №3 работает по оценкам |
| **1.6** | Надёжность и онбординг: DLQ, почасовая сверка, алерты в чат Б24, подключение трёх клиентов | | сверка зелёная, алерт приходит при остановленном воркере |

⚠ **Интерфейсы (1.2, 1.4, 1.5) — на `@bitrix24/b24ui`**, UI-kit Битрикс24 (решение
владельца 2026-08-27). Он под Vue/Nuxt, то есть первый же экран возвращает Nuxt в стек,
из которого он был сознательно исключён («интерфейса у сервиса нет»). Это не возражение,
а цена, которую стоит увидеть заранее: с ней меняются сборка, образ и время деплоя.

После **1.3** можно начинать «тихий» пилот на одном лояльном клиенте, доделывая
1.4–1.6 при живой работе. Это и есть смысл порядка: контрольная точка не в конце этапа.

⚠ **Что уже сделано и переиспользуется** — приём событий, очередь, хранение токенов,
журнал, деплой, CI (таблица в [`PRODUCT.md`](PRODUCT.md)). План работ в
[`spec/work-plan-stage1.md`](spec/work-plan-stage1.md) писался без этого знания: его
фазы 0.1 и 1.1–1.3 у нас закрыты этапом 0, и их оценки к нам не относятся.

⚠ **До начала 1.3 нужно решение по хранилищу.** Спецификация (решение Б2) кладёт связку
тикет↔issue в UF-поля задач; работает ли поиск по ним — открытый вопрос, перемер делает
`make uf-probe`, разбор в [`PRODUCT.md`](PRODUCT.md). От ответа зависит, на чём строится
почасовая сверка из критериев приёмки этого этапа.

## Этап 2. Биллинг

Раздел 8 спецификации: агрегация часов, согласование детализации, инвойс в нашей CRM,
печатные формы, оплата.

**Цель.** Счёт по проекту собирается сам из закрытых тикетов и уходит клиенту с
детализацией, в которой каждая строка — ссылка на тикет.

**Выгоды.**

- **Владельцу:** конец месяца перестаёт быть отдельной работой; видно выручку и
  утилизацию в разрезе проектов, а также долю бесплатных переделок — то есть цену
  собственных ошибок.
- **Клиенту:** счёт не приходит сюрпризом: видно, за что именно платит, и спорную строку
  можно снять, не блокируя остальной счёт.
- Просрочка перестаёт быть неудобным разговором: приостановка приёма работ — пункт
  договора и флаг проекта, а не решение в моменте.

**Критерии приёмки:**

- В расчётный день по каждому активному проекту собран счёт из закрытых оплачиваемых
  тикетов с пустым `UF_BILLED_IN`; тикет не попал в два счёта.
- Пакетная модель списала включённые часы и посчитала превышение по ставке overage.
- Тикет с подтверждённой оценкой попал в счёт **по оценке**, а не по факту.
- Тикет-доработка после негативного отзыва в счёт **не попал**.
- Спорная строка перенесена в следующий период, остальной счёт выставлен.
- Инвойс создан в CRM, все выбранные печатные формы сгенерированы и приложены к нему.
- Отсутствие реакции клиента 5 рабочих дней привело к автосогласованию; просрочка 15
  календарных дней подняла флаг «приостановить приём работ».
- У клиента с двумя проектами получилось **два независимых счёта**.

## Этап 3. AI-контур

Раздел 7 спецификации: три точки — приём, разбор падения тестов, закрытие.

**Цель.** AI снимает рутину чтения и сочинения текстов, не принимая ни одного решения.

**Выгоды.**

- Обращение приходит уже с типом, приоритетом и списком похожих закрытых тикетов —
  дубликат виден до того, как на него потратили час.
- Красные Actions приходят с разбором лога, а не со ссылкой на лог.
- Итог клиенту и строки акта пишутся черновиком, человек их правит, а не сочиняет.

**Критерии приёмки:**

- Флаг «AI-анализ» в карточке проекта выключен → ни одна из трёх точек не вызвана.
- Недоступность AI не остановила конвейер: тикет создан, issue создан, статус ушёл.
- Предложение «это дубликат открытого тикета» показано до создания.
- Черновик итога и строки акта выданы и правятся человеком до отправки.
- Состав промпта зафиксирован документом и проверен на тестовом тикете: наружу уходят
  тема, описание и тип, но не ФИО, не контакты из переписки и не вложения. Ссылки на
  договор недостаточно — граница должна быть технической и предъявимой.

## Этап 4. Маркетплейс

Решения Б7, Б8, А12: публикация одного приложения с двумя частями.

**Цель.** Клиент подключается в один клик из маркетплейса, а не заводит локальное
приложение руками.

**Выгоды.**

- Онбординг перестаёт быть работой на двоих: сейчас каждый клиент заводит своё
  приложение со своей парой ключей — двадцать клиентов это двадцать таких заходов.
- Обновления перестают требовать перемодерации: в маркете только манифест, весь UI
  грузится с нашего сервера (решение Б8).
- Появляется витрина: приложение видно тем, кто нас ещё не знает.

**Критерии приёмки:**

- Приложение прошло модерацию по настоящему потоку на тестовом проекте (не имитация).
- Установка на чистый портал прошла без нашего участия.
- Обновление UI выехало без перемодерации.
- `ONAPPUNINSTALL` удаляет токены сразу, проект помечается «приложение удалено»,
  история остаётся у нас; политика обработки данных опубликована.
