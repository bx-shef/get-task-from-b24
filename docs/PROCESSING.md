# Обработка события: от задачи клиента до задачи у нас

> Last reviewed: 2026-08-26

**Главный доменный документ.** Что происходит между событием на портале клиента и
созданной задачей в нашем Битрикс24: критерии отбора, перенос полей, очередь,
уведомление в Telegram, ошибки.

> ⬜ Помеченное так — не решено, ждёт ответа владельца. Открытые вопросы собраны в конце.

## Общая схема

```
Портал клиента (локальное приложение «только API»)
        │  ONTASKADD (POST, в теле только ID задачи)
        ▼
  наш обработчик  ──▶ ответ 200 сразу, до всякой работы
        │                (события Б24 НЕ ретраятся: медленный или упавший
        │                 ответ = задача потеряна молча)
        ▼
     ОЧЕРЕДЬ
        │  1. tasks.task.get на портале клиента — вычитать поля
        │  2. проверить критерии
        │  3. дедуп по журналу (портал + ID задачи)
        │  4. tasks.task.add в нашем Б24 (входящий вебхук)
        │  5. сообщение в Telegram
        ▼
   Наш Битрикс24
```

⚠ **Обработчик не делает работу — он её ставит в очередь.** В событии приходит только
`ID` (см. [`B24_EVENTS.md`](B24_EVENTS.md)), значит каждая обработка — минимум два
похода по сети (чтение у клиента + запись у нас) плюс Telegram. Делать их в
синхронном ответе нельзя: любой таймаут у клиента или у нас превращается в
безвозвратно потерянную задачу.

## Критерии отбора

Задача переносится, только если выполнены **оба** условия:

1. **Название начинается с `#support`.**
2. **Исполнитель задачи** (`responsibleId`) равен «особому» id, указанному для этого
   портала в переменных окружения рядом с доменом.

Не прошло хотя бы одно — событие считается обработанным и **успешно** отбрасывается
(это норма, а не ошибка: на портале клиента задачи создаются постоянно).

⚠ **Портал, которого нет в списке поддерживаемых, — тоже отказ**, даже если событие
подписано и подлинно. Список из окружения — это и есть перечень тех, кого мы
обслуживаем.

⚠ **Сравнение названия точное по префиксу.** Хвост после `#support` не трогаем.
⬜ Не решено: учитывать ли регистр (`#Support`), допускать ли пробелы перед `#`,
переносить ли префикс в название у нас или срезать его.

⚠ **`responsibleId` — id на портале КЛИЕНТА.** У нас на портале такого пользователя
нет и быть не должно; для сопоставления он не годится ни в каком виде.

## Что переносим

| Из задачи клиента | Куда у нас | Примечание |
|---|---|---|
| название | `title` задачи | ⬜ с префиксом `#support` или без |
| содержание | `description` | |
| кто поставил (постановщик) | **в текст `description`** | ⚠ не в `creatorId` — см. ниже |
| крайний срок | `DEADLINE` | ⬜ что делать, если срока нет |
| какой Б24 (домен клиента) | **в текст `description`** | ⬜ или отдельное поле/тег |
| ссылка на задачу у клиента | **в текст `description`** | `https://<домен>/company/personal/user/<id>/tasks/task/view/<taskId>/` |

⚠ **«Кто поставил» нельзя положить в `creatorId`.** Это идентификатор сотрудника
**нашего** портала; id постановщика с портала клиента там означал бы другого человека
или ошибку метода. Имя постановщика переносим текстом. Тот же довод касается
исполнителя: у нас задачу создаёт вебхук, и `responsibleId` — наш сотрудник.
⬜ Кто именно назначается исполнителем у нас — не решено (одна константа из
окружения? владелец вебхука по умолчанию?).

⚠ **Домен клиента и ссылка обязаны быть в задаче.** Порталов 20–30; задача «сделай
поддержку» без указания, чья она, бесполезна ровно настолько, насколько трудно это
потом восстановить.

## Дедупликация

Журнал: `домен (или member_id) клиента + ID задачи-источника → ID задачи у нас`.
Проверяется **до** создания; повторная доставка события возвращает уже созданный id и
второй задачи не заводит. Без журнала дубли заметит человек, а не тест.

⬜ Не решено, где журнал живёт (БД или файл/Redis) — вместе с выбором стека.

## Уведомление в Telegram

После успешного создания задачи — сообщение «задача создана, иди делай»: название,
клиент, ссылка на задачу **у нас** и ссылка на задачу **у клиента**.

⚠ **Telegram — отдельный шаг, а не часть создания.** Упавший Telegram не должен
приводить к повторному созданию задачи: сообщение ретраится само по себе, задача — нет.

⬜ Не решено: куда шлём (личка/группа/канал), одно направление на всех клиентов или
разные, шлём ли сигнал об ошибках переноса туда же.

## Ошибки

| Что случилось | Что делаем |
|---|---|
| критерии не прошли | успешный отказ, ничего не создаём, в журнал — строкой |
| портал не в списке | то же |
| `tasks.task.get` у клиента упал | ретрай с задержкой; исчерпали — сигнал оператору |
| наш Б24 недоступен | ретрай; задача уже принята, терять её нельзя |
| задача уже переносилась | ничего не делаем, это норма |
| Telegram упал | ретрай только сообщения |

⚠ **«Событие принято» и «задача создана» — разные состояния**, и второе может не
наступить часами. Значит нужно место, где видно застрявшие события, иначе про потерю
узнаёт клиент.

## Открытые вопросы

1. **Домен обработчика.** В задании указан `client-bank-alfa-by.bx-shef.by` — это домен
   соседнего проекта. Похоже на опечатку; нужен домен этого сервиса.
2. **20–30 порталов × локальное приложение = 20–30 пар `client_id`/`client_secret`**
   плюс токены на каждый. Держать это всё в окружении тяжело — см.
   [`CLIENT_APP.md`](CLIENT_APP.md), там разобраны варианты.
3. Регистр и форма префикса `#support`; срезаем ли его в названии у нас.
4. Исполнитель и группа/проект создаваемой задачи у нас.
5. Поведение при отсутствии крайнего срока у задачи клиента.
6. Нужны ли `ONTASKUPDATE`/`ONTASKDELETE` (синхронизация после переноса) — сейчас
   вынесены в [`IDEAS.md`](IDEAS.md).
