# Система работы с обращениями: спецификация

**Версия 1.3 — 01.08.2026.** Методы сверены с документацией REST API (см. приложение b24-api-mapping.md). Собственная СУБД исключена: состояние — в Б24, env и Redis. Все 25 вопросов чек-листа решены; документ готов к разбивке на этапы разработки.

Стек: Битрикс24 (маркетплейс-приложение, две части) · GitHub (App, Issues, Actions) · бэкенд Node.js в Docker на `support.bx-shef.by` · Redis + BullMQ (без собственной СУБД) · AI через AI-роутер Б24 / DeepSeek

## 1. Компоненты

Система состоит из четырёх частей, и вся логика живёт только в одной из них.

1. **Приложение** — одно приложение Б24 из маркетплейса с **двумя частями**:
   - **Клиентская** — на порталах клиентов (десктоп и мобильный клиент Б24, одна адаптивная страница): создание тикета, список и карточка тикетов с перепиской, счета. Портал без активного проекта видит экран «свяжитесь с нами» вместо формы.
   - **Операторская** — на вашем портале: работа с тикетами идёт в штатных задачах и чатах Б24, приложение добавляет пункты меню сообщений («Отправить клиенту», «Отправить в issue»), экраны настроек (шаблоны печатных форм, параметры) и служебные интерфейсы.
   Логики ни одна часть не содержит — только UI и вызовы бэкенда.
2. **Бэкенд** — ваш сервер. Держит всю бизнес-логику, очередь и маппинг статусов; собственной СУБД нет — конфигурация и стартовые токены в env-файле, обновляемые токены и очередь в Redis (AOF), связки тикет↔issue в полях задач и карточек проектов Б24. Единственный компонент, который ходит в Б24 и GitHub. **Стек: Node.js, упаковка в Docker, существующий сервер, домен `support.bx-shef.by`, TLS — бесплатный сертификат (Let's Encrypt с автопродлением).**
3. **Ваш Б24** — задачи (тикеты), смарт-процессы «Клиенты» и «Проекты» (реестр), CRM (инвойсы и печатные формы).
4. **GitHub** — один GitHub App, установленный в репозитории клиентов. Issues, Pull Requests, Actions (деплой и тесты).

## 2. Реестр: два смарт-процесса

Модель трёхуровневая: **клиент → проект → тикет**. Клиент — это портал и организация; проект — это договор плюс репозиторий. У клиента может быть несколько проектов.

### Смарт-процесс «Клиенты»

Один элемент на клиента, ключ поиска — `member_id` портала. Создаётся автоматически по событию `ONAPPINSTALL`, дозаполняется вручную.

Поля: организация, `member_id`, домен портала, реквизиты, контактные лица, email для документов, ответственный с вашей стороны, активность.

### Смарт-процесс «Проекты»

Элементы привязаны к клиенту (поле-связка). Всё, что раньше висело на клиенте про договор и Git, живёт здесь.

Поля: клиент (связка), название проекта, **договор**: номер и дата, тарифная модель (пакет часов / T&M / фикс / абонентка), ставка и валюта, включённые часы в месяц, правило переноса остатка, ставка сверх пакета, расчётный день, порог автосогласования счёта, порог согласования оценки (часы), срок действия, активность; **Git**: репозиторий (`owner/repo`), ID установки GitHub App (репозитории принадлежат клиентам — App устанавливает клиент по ссылке-приглашению при онбординге; Actions-минуты и секреты деплоя на его стороне); **задачи и роли**: группа в вашем Б24, исполнитель, контролёр (постановщик задач), **менеджер проекта** (ответственный за инвойсы и акты).

Тикет всегда привязан к проекту (`UF_TICKET_PROJECT`), и через проект однозначно резолвятся и репозиторий для issue, и договор для биллинга. Клиент в форме выбирает проект, если активных проектов больше одного.

## 3. Тикет

**Инвариант: 1 тикет = 1 задача в вашем Б24 = 1 issue в GitHub.** Номер тикета — ID задачи. Он же в заголовке issue: `[T-1042] Тема`.

### Поля формы

| Поле | Обязательное | Примечание |
|---|---|---|
| Проект | да | Скрыт, если у клиента один проект |
| Тип: ошибка / доработка / вопрос | да | Чипы на мобильном, select на десктопе |
| Тема | да | |
| Описание | да | |
| Приоритет | да | Дефолт «средний» |
| Скриншоты, файлы | нет | На Диск вашего Б24, в issue — ссылки |
| Ссылка, шаги воспроизведения | нет | На мобильном — в свёрнутом блоке |
| Родительский тикет | — | Скрыт, ставится системой при доработке |

Автор определяется из авторизации Б24. В списке проектов показываются только активные (договор действует). Идемпотентность создания: ключ `project_id + hash(тема + описание) + минута`.

### Служебные UF-поля задачи

`UF_TICKET_PROJECT` (ID элемента «Проекты» — главная связка, клиент и договор резолвятся через неё), `UF_TICKET_PARENT`, `UF_ISSUE_NUMBER`, `UF_BILLED_IN` (номер счёта), `UF_ESTIMATE` (согласованная оценка, часы), `UF_ESTIMATE_APPROVED` (дата подтверждения клиентом), `UF_AI_TYPE`, `UF_AI_SIMILAR`, `UF_AI_CONFIDENCE`. Часы отдельным полем не дублируются — источник трудозатрат один: **штатный учёт времени задачи Б24** (затраченное время из тайм-трекинга и записей `task.elapseditem`). Закрыть задачу с нулевым затраченным временем по оплачиваемому тикету нельзя — валидация на бэкенде.

### Переписка в тикете

В карточке тикета в приложении клиента — лента комментариев с вложениями (вложения на Диск, как при создании).

- **Ваша сторона — чат задачи.** Вся переписка ведётся в чате задачи и по умолчанию внутренняя. Приложение добавляет в контекстное меню сообщения два пункта: **«Отправить клиенту»** и **«Отправить в issue»** — синхронизация ручная, посообщенная, одно сообщение можно отправить в оба адреса. «Отправить клиенту» публикует сообщение в карточке тикета и шлёт клиенту пуш `im.notify`; «Отправить в issue» добавляет комментарий в GitHub issue.
- **Клиент → вам**: комментарий из карточки тикета попадает в чат задачи с пометкой «от клиента» и уведомлением ответственному. В issue автоматически не дублируется — при необходимости пересылается тем же пунктом «Отправить в issue».
- Комментарий клиента в тикете со статусом «На проверке» или «Решён» — уведомление ответственному и контролёру; автопереоткрытия нет, решение за человеком (при необходимости — правило 3 из раздела 5).
- Реализация меню — через placement Б24 для сообщений чата; доступность в чате задачи и в мобильном клиенте проверить на прототипе, запасной вариант — кнопки у комментария в ленте задачи с той же логикой.

## 4. Жизненный цикл и статусы

| Событие GitHub | Задача в вашем Б24 | Статус клиенту |
|---|---|---|
| — (доработка выше порога) | Оценка | Ждёт подтверждения оценки |
| Issue создан | Новая | Принят в работу |
| Ветка / коммиты / PR открыт | В работе | В работе |
| PR смержен → Actions: деплой и тесты зелёные | Ждёт контроля | На проверке |
| Контроль принял → issue закрыт | Завершена | Решён + текст итога |
| Клиент отклонил оценку | Завершена (отменена) | Отменён |
| — (тикет-доработка после отзыва) | Новая | В работе (доработка) |

**Стадия «Оценка»** — только для типа «доработка» с оценкой выше порога согласования (порог в часах — поле договора проекта; доработки ниже порога, баги и вопросы идут в работу сразу). Ответственный проставляет оценку часов (`UF_ESTIMATE`) и при необходимости короткий план; клиенту — пуш «Оценка: N часов ≈ сумма» с кнопками «Подтвердить / Отклонить» и возможностью задать вопрос через переписку. Подтвердил (`UF_ESTIMATE_APPROVED` = дата) → создаётся issue, обычный цикл. Отклонил → тикет закрывается со статусом «Отменён», в биллинг не попадает. Нет ответа — тикет ждёт, напоминание клиенту через 3 дня. **Issue до подтверждения оценки не создаётся.**

**Среда деплоя одна — продакшен.** Мердж PR запускает Actions: деплой в прод + автотесты; контролёр принимает работу уже на проде. Следствия, заложенные в процесс: приоритет зелёных автотестов (упали — деплой не считается состоявшимся, правило 1 раздела 5), у workflow должен быть job отката на предыдущий релиз, и рискованные доработки по возможности закрываются feature-флагом до приёмки. Staging может появиться позже как настройка проекта без изменения схемы статусов.

Клиент видит только статусы правого столбца (семь). Смена клиентского статуса — пуш через `im.notify` на портал клиента; при «Решён» дополнительно текст итога и кнопки отзыва.

**Контроль** — через штатный механизм Б24: бэкенд создаёт задачу с постановщиком-контролёром (`CREATED_BY` = контролёр из карточки проекта), исполнителем-разработчиком и флагом «Принять работу после завершения» (`TASK_CONTROL`). Когда исполнитель завершает задачу, она штатно переходит в «Ждёт контроля»; постановщик принимает её (задача закрывается → бэкенд закрывает issue и шлёт клиенту «Решён») или возвращает на доработку штатной кнопкой (→ правило 2 раздела 5). Лимит на приёмку: 1 рабочий день, при превышении — напоминание постановщику.

## 5. Возвраты — три правила

1. **Тесты упали** (Actions красные): задача остаётся «В работе», issue переоткрывается, AI пишет разбор падения комментарием. Клиент ничего не видит.
2. **Контроль не принял**: то же самое — задача обратно «В работе», тот же issue переоткрыт, комментарий с причиной. Клиент видит «В работе».
3. **Клиент не принял после закрытия** (отзыв «не решено» или новое обращение по теме): создаётся **новый тикет** с `UF_TICKET_PARENT` = старый. У него свой issue. Часы по нему по умолчанию неоплачиваемые (ручное переопределение возможно, если это фактически новые требования).

Новые issue внутри старого тикета не создаются никогда.

## 6. Отзыв

После статуса «Решён» в карточке тикета две кнопки (решено / не решено) и поле комментария, при негативном — комментарий обязателен. Результат пишется в UF-поля задачи и агрегируется в смарт-процесс (CSAT клиента). Негативный отзыв запускает правило 3 из раздела 5.

## 7. Контур AI

AI советует, но не решает. Все вызовы асинхронные, через очередь бэкенда; недоступность AI не блокирует конвейер. Включается флагом «AI-анализ» в карточке проекта — при выключенном флаге точки 1–3 для тикетов проекта не вызываются. Три точки:

1. **Приём.** Вход: текст, вложения, история клиента. Выход: тип, приоритет, похожие тикеты (по базе закрытых), черновик ответа, если это типовой вопрос. Дубликат открытого тикета → предложение привязать вместо создания. Результат — в UF-поля и первым комментарием задачи и issue.
2. **Падение тестов.** Вход: лог Actions + diff PR. Выход: комментарий-разбор в задачу.
3. **Закрытие.** Выход: черновик итога для клиента человеческим языком, названия строк для акта, флаг неправдоподобных часов (правится вами до отправки). Закрытый тикет индексируется в базу знаний для точки 1.

## 8. Контур биллинга

**Единица биллинга — проект (договор), не клиент.** Счёт формируется по одному проекту; у клиента с двумя проектами — два независимых счёта, каждый по своему тарифу и в свой расчётный день. Пакет часов тоже считается на проект.

Источник часов для счёта: у тикетов с согласованной оценкой (`UF_ESTIMATE_APPROVED`) — **оценка**, фактическое затраченное время на цену не влияет (риск превышения ваш); у остальных оплачиваемых тикетов — **затраченное время задачи** (штатный учёт времени Б24) на момент закрытия. Если по ходу работ видно серьёзное превышение оценки — ответственный отправляет клиенту обновлённую оценку на повторное подтверждение до продолжения работ (тот же механизм стадии «Оценка»). Тариф берётся из договора проекта, фиксируется в тикете на момент закрытия и задним числом не пересчитывается.

Цикл, в расчётный день каждого активного проекта:

1. **Агрегация**: все закрытые оплачиваемые тикеты проекта за период с пустым `UF_BILLED_IN`. Для пакетной модели — сначала списание включённых часов, превышение по ставке overage. Тикеты-доработки (правило 3) — бесплатны, если не переопределено.
2. **Согласование**: детализация (тикет → тема → часы → сумма, каждая строка со ссылкой на тикет) на экране «Счета» в приложении клиента + пуш. Спорные строки клиент помечает комментарием — они переносятся в следующий период, остальное выставляется. Одна спорная строка не блокирует счёт. Нет реакции **5 рабочих дней** → автосогласование (пункт договора). Суммы ниже порога (поле проекта, для пилота 500 BYN) — без согласования.
3. **Документы**: бэкенд создаёт **инвойс (смарт-счёт) в вашей CRM**: товарные позиции = задачи (название строки — из AI-черновика или темы тикета), количество = согласованная оценка (`UF_ESTIMATE`) для подтверждённых доработок, иначе **затраченное время задачи** (учёт времени Б24), цена = ставка часа из параметров проекта. Привязка к элементу «Проекты», номер договора в шапке. **Печатные формы генерируются штатным генератором документов Б24 относительно инвойса.** В настройках приложения выбирается **несколько шаблонов** (список из `crm.documentgenerator.template.list`, выбор глобальный с переопределением на проекте) — сразу после создания инвойса приложение **автоматически генерирует все выбранные формы** (`crm.documentgenerator.document.add` по каждому шаблону) и прикладывает их к инвойсу (PDF генерируется асинхронно — опрашивать `crm.documentgenerator.document.get` до готовности). Ответственный за инвойс — **менеджер проекта** (поле в карточке «Проекты»): он проверяет готовый комплект и отправляет клиенту. После его отметки об отправке статус счёта в приложении клиента — «Выставлен». **ЭДО в v1 не интегрируется**: акт подписывается привычным клиенту способом (бумага, скан, собственный ЭДО клиента), менеджер отмечает «акт подписан» чекбоксом в инвойсе — эта отметка закрывает документооборот по счёту. В тикеты пишется `UF_BILLED_IN`.
4. **Оплата**: статус в CRM → по вебхуку в приложение клиента. Напоминания: за 3 дня, в день срока, далее еженедельно. Просрочка **15 календарных дней** → флаг «приостановить приём работ» на уровне проекта (пункт договора).

Из тех же данных: вам — выручка и утилизация в разрезе проектов и клиентов, доля бесплатных переделок; клиенту — виджет остатка часов по каждому проекту и история счетов. Окончание срока договора (за 30 дней) — напоминание вам о продлении; по истёкшему договору форма создания тикета блокируется с сообщением клиенту.

## 9. События и вебхуки

**Входящие в бэкенд:**

| Источник | События | Реакция |
|---|---|---|
| Портал клиента | `ONAPPINSTALL`, `ONAPPUNINSTALL` | Создать/деактивировать элемент реестра, сохранить токены |
| Ваш Б24 | `ONTASKUPDATE`, `ONTASKCOMMENTADD` | Синхронизация статуса и комментариев в issue |
| Ваш Б24 (CRM) | `onCrmDynamicItemUpdate` (ENTITY_TYPE_ID = 31, смарт-счёт) | Статус оплаты клиенту |
| GitHub App | `issues`, `pull_request`, `workflow_run` | Смена статусов задачи по разделу 4 |

**Исходящие:** REST в порталы клиентов (`im.notify.system.add`, данные для экранов приложения), REST в ваш Б24 (`tasks.task.*`, `crm.item.*`, Диск), GitHub API (`issues`, комментарии), AI-сервис.

## 10. Принципы надёжности

- Идемпотентность всех создающих операций (тикет, issue, счёт) по естественным ключам.
- Очередь с ретраями на каждый внешний вызов; падение GitHub или AI не теряет тикет.
- Сверка раз в час: задача без issue, issue без задачи, закрытый тикет без часов.
- Лог всех вебхуков с телом запроса — структурированный JSON в stdout; ротация драйвером Docker `json-file` (`max-size: 50m`, `max-file: 5`).
- Файлы хранятся один раз — на Диске вашего Б24; везде остальное — ссылки.

## 11. Решённые развилки

- Канал — только приложение Б24 (десктоп + мобильный клиент), Telegram исключён.
- Git — GitHub: один GitHub App, Issues + PR + Actions.
- Мультипроектность — да: смарт-процесс «Проекты», договор и репозиторий на проекте, биллинг по проекту.
