# План работ: этап 1 — запуск пилота

Приложение к спецификации v1.2. Цель — **максимально быстрый старт пилота** на трёх клиентах: контур тикетов (разделы 1–6 спецификации) без биллинга и AI. Оценки — в рабочих днях одного разработчика; при параллельной работе с помощником фронт и бэк разводятся по трекам.

Принцип плана: сначала снять два технических риска прототипами, дальше строить систему вертикальными срезами — каждый срез заканчивается работающим сквозным сценарием, чтобы пилот можно было начать даже до полной готовности всех функций.

## Фаза 0. Прототипы рисков — 2–3 дня

Делается до основного кода. Если что-то не подтвердится, меняем механику по запасным вариантам из спецификации, пока это дёшево.

| # | Задача | Проверяем | Готово, когда |
|---|---|---|---|
| 0.1 | Каркас: локальное приложение на вашем портале + туннель на `support.bx-shef.by` | OAuth, event.bind, placement.bind живьём | Приложение ставится, события приходят |
| 0.2 | Прототип `IM_CONTEXT_MENU` | Появляется ли пункт меню в **чате задачи**; работает ли в **мобильном клиенте**; что приходит в handler (ID сообщения, текст, чат) | Пункт виден, handler получает данные сообщения |
| 0.3 | Прототип входящих: какой канал слушать для комментариев задачи (форум-комментарии vs сообщения чата задачи), событие и состав данных | Выбор механики «от клиента» | Комментарий ловится с текстом и автором |
| 0.4 | GitHub App-заглушка: регистрация, установка в тестовый репозиторий, вебхуки `issues`/`pull_request`/`workflow_run` доходят до сервера | Права из Б5 достаточны | Issue создаётся, события приходят |

Результат фазы: решения по пунктам 5.1–5.2 карты API зафиксированы, схема env сверена с вашим MVP, запасные варианты либо отброшены, либо активированы.

## Фаза 2. Срез «тикет проходит насквозь» — 4–5 дней

Самый важный срез: после него система в принципе работает.

| # | Задача | Примечания |
|---|---|---|
| 2.1 | Форма создания тикета (десктоп-вёрстка): проект, тип, тема, описание, приоритет, свёрнутый блок, загрузка файлов на Диск | Идемпотентность по ключу из раздела 3 |
| 2.2 | Создание задачи: `tasks.task.add` с `CREATED_BY` = контролёр, `taskControl: Y`, группа проекта, привязка `UF_CRM_TASK = T{hex}_{id}` | Проверить достаточность штатной привязки вместо `UF_TICKET_PROJECT` |
| 2.3 | Создание issue в репозитории проекта: `[T-{id}] Тема`, тело со ссылками на файлы | Через installation token GitHub App |
| 2.4 | Маппинг статусов: вебхуки GitHub (`pull_request` merged, `workflow_run`) + `onTaskUpdate` → статус клиенту по таблице раздела 4 | Ветка `ticket/{id}`, `Closes #N` (Б6) |
| 2.5 | Список и карточка тикета у клиента: статусы, история | |
| 2.6 | Пуши `im.notify` при смене клиентского статуса | |
| 2.7 | Контроль: завершение исполнителем → статус 4 → приёмка/возврат контролёром (штатно + `approve/disapprove`), закрытие issue, «Решён» клиенту | Правила 1–2 раздела 5 |

Контрольная точка: **сквозной сценарий** — тикет из формы → задача + issue → ветка → PR → мердж → Actions → контроль → «Решён» у клиента. С этого момента можно начинать «тихий» пилот на одном лояльном клиенте, параллельно доделывая фазы 3–4.

## Старт пилота

Суммарно до старта: **17–23 рабочих дня** (3,5–4,5 недели одним разработчиком); при раннем «тихом» старте после фазы 2 первый клиент живёт в системе уже через ~2 недели. Пилот — 2–4 недели живой работы (Б10), в это время параллельно готовится этап 2 (биллинг) и досье для маркетплейса (Б7: тестовый проект, сценарий модерации, политика данных из А12).

## Вне этапа 1 (не делать сейчас)

Биллинг и документы (этап 2), AI-контур (этап 3), публикация в маркетплейсе (этап 4 — до неё пилотные порталы работают с приложением, установленным напрямую), SLA, ЭДО, staging, роли, режим отсутствия.

## Критический путь и риски

Критический путь: 0.2/0.3 (механика переписки) → 1.3 (OAuth) → 2.2–2.4 (сквозная связка) → 5.3 (онбординг). Главные риски: `IM_CONTEXT_MENU` не работает в чате задачи (запас: кнопки у комментария, +1 день); клиент затянет установку GitHub App в свой репозиторий (митигируется: ссылка-приглашение готовится в фазе 0.4 и отправляется клиентам заранее, вместе с допсоглашениями); Actions-workflow деплоя на стороне клиентов различается (закладывать шаблон workflow per-проект, а не общий).
