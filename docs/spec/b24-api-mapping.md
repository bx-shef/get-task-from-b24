# Карта REST API Битрикс24 для системы обращений

Приложение к спецификации v1.1. Сверено с официальной документацией apidocs.bitrix24.ru, 01.08.2026.

## 1. Подтверждённые узлы

| Узел спецификации | Метод / событие / placement | Примечания |
|---|---|---|
| Пункты меню «Отправить клиенту / в issue» (А3) | placement **`IM_CONTEXT_MENU`** через `placement.bind` | Официальный виджет контекстного меню сообщения чата. HANDLER — URL на нашем сервере; OPTIONS: context, role, extranet |
| Чат задачи | Поле **`chatId`** в `tasks.task.get` (новая карточка задач); отправка — **`tasks.task.chat.message.send`** | Чат задачи адресуется и через `im.*` по `chatXXX` |
| Создание тикета-задачи | `tasks.task.add` | Поля подтверждены: `CREATED_BY` (постановщик = контролёр), `RESPONSIBLE_ID`, `GROUP_ID`, `PRIORITY` (0/1/2), UF-поля |
| Контроль (А1) | Поле **`taskControl`** = `Y`; статус задачи **`4` = «ожидает контроля»**; приёмка/возврат — **`tasks.task.approve` / `tasks.task.disapprove`** | Всё штатное, включая API-методы приёмки — при желании кнопку «принять» можно дать контролёру и в нашем UI |
| Затраченное время (А2) | Поле задачи **`timeSpentInLogs`** (секунды, факт); записи — методы раздела «Затраченное время» (`task.elapseditem.*`); `timeEstimate` — оценка в секундах | `timeEstimate` можно использовать как зеркало `UF_ESTIMATE` для видимости в карточке задачи |
| Привязка задачи к проекту | Штатное поле **`UF_CRM_TASK`** со значением `T{hex}_{id}` — привязка к элементу смарт-процесса | Бонус: связь видна в интерфейсе Б24 без нашего кода; `UF_TICKET_PROJECT` можно не заводить, использовать штатную привязку |
| Смарт-процессы «Клиенты», «Проекты» | `crm.type.add` → `entityTypeId`; поля — `userfieldconfig.add`; элементы — `crm.item.*`; краткий код типа `T{hex}` (`crm.enum.ownertype`) | Стадии при необходимости — `crm.category.add`, `crm.status.add` |
| Инвойс (А2) | **Смарт-счёт `entityTypeId = 31` (SMART_INVOICE)** через `crm.item.add` | Старый тип счетов (5) не использовать. Товарные позиции — `crm.item.productrow.*` |
| Печатные формы (А2) | **`crm.documentgenerator.template.list`**, **`crm.documentgenerator.document.add`** (по каждому выбранному шаблону), нумерация — `crm.documentgenerator.numerator.*`, публичная ссылка — `...document.enablepublicurl` | ⚠️ Методы с префиксом `crm.` — в спецификации были указаны без него. ⚠️ `pdfUrl` появляется асинхронно — после `document.add` опрашивать `document.get` до готовности PDF |
| События задач | `event.bind`: **`onTaskUpdate`** (FIELDS_BEFORE/AFTER), события комментариев — раздел «Комментарии» задач | По `onTaskUpdate` приходят только ID — состояние дочитывать `tasks.task.get` |
| События смарт-процессов и инвойса | **`onCrmDynamicItemAdd / Update / Delete`** — для смарт-процессов **и смарт-счетов** | ⚠️ `ONCRMDEALUPDATE` из спецификации не подходит: у нас нет сделок, а динамические события для системных типов не вызываются. Статус оплаты инвойса ловим `onCrmDynamicItemUpdate` с фильтром `ENTITY_TYPE_ID = 31`. Существует подписка на конкретный тип: `onCrmDynamicItemUpdate_{entityTypeId}` (работает из приложений, в UI не выводится) |
| Установка/удаление | `ONAPPINSTALL`, `ONAPPUNINSTALL` | Стандартные события приложений |
| Уведомления клиенту | `im.notify.system.add` | |
| Мобильная часть (клиентская) | Опция **«Встраиваться в BitrixMobile»** в кабинете разработчика + встройка `mobile` | Требование: основной функционал адаптирован под мобильное приложение |
| Модерация/кабинет | Опции: своя страница и пункт меню, встройка виджетов, «может устанавливать любой пользователь» | Последняя опция важна для А6 («создают все»): по умолчанию ставит только админ |

## 2. Исправления, внесённые в спецификацию

1. Раздел 9: `ONCRMDEALUPDATE` → `onCrmDynamicItemUpdate` (ENTITY_TYPE_ID = 31, смарт-счёт).
2. Раздел 8: методы генератора документов получили корректный префикс `crm.documentgenerator.*`; добавлено ожидание асинхронного PDF.

## 3. Возможные упрощения (решить при проектировании)

- **`UF_CRM_TASK` вместо `UF_TICKET_PROJECT`**: штатная привязка задачи к элементу «Проекты» — связь видна в карточке задачи и кликабельна. Кастомное поле тогда не нужно.
- **`timeEstimate` как хранилище оценки**: оценка часов видна в самой задаче штатно; `UF_ESTIMATE` остаётся только если нужна отдельная от плановой оценка.
- **`tasks.task.approve/disapprove`**: кнопки приёмки контролёра можно продублировать в нашем UI, не заставляя его открывать задачу.

## 4. Нюансы из документации, влияющие на код

- Токены авторизации **не всегда передаются в обработчик события** — если хит не привязан к пользователю. Полагаться только на токены, сохранённые при установке (у нас так и заложено).
- События не отправляются, пока установка приложения не завершена (`ONAPPINSTALL` → подтвердить установку).
- Системные поля `UF_CRM_TASK`, `UF_TASK_WEBDAV_FILES` не возвращаются по умолчанию — явно указывать в `select`.
- Лимиты REST: страница apidocs.bitrix24.ru/limits.html — учесть в настройках очереди (rate limit на портал).
- У Битрикса есть **официальный MCP-сервер документации** (apidocs.bitrix24.ru/ai-tools/mcp.html) — стоит подключить в среду разработки, чтобы AI-агент сверялся с документацией при написании кода.

## 5. Остаётся проверить прототипом (не нашлось в документации однозначно)

1. **`IM_CONTEXT_MENU` в чате задачи и в мобильном клиенте** — placement описан для чатов вообще; работа именно в чате задачи и на мобильном требует проверки. Запасной вариант зафиксирован в спецификации (кнопки у комментария).
2. Событие на **комментарий в чате задачи** для входящих: комментарии задачи (форум) vs сообщения чата задачи — какой канал слушать для пометки «от клиента», выяснить на прототипе.
3. Поведение `crm.item.productrow` у смарт-счёта при валюте проекта ≠ валюте портала.
