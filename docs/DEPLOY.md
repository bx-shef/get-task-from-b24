# Деплой

> Last reviewed: 2026-08-26

Схема та же, что в `client-bank-alfa-by`: **CI собирает образ → GHCR → Watchtower на
сервере подхватывает → общий nginx-proxy отдаёт наружу по TLS**. Ручных шагов на сервере
после первичного развёртывания нет.

Артефакты в репозитории: `Dockerfile` (Node 22 alpine, non-root), `docker-compose.prod.yml`
(app + Postgres + Redis), `Makefile` (единственный интерфейс к серверу).

## Конвейер

```
PR      → ci (lint + test + typecheck + build; тесты — против настоящего Postgres) + docker-build без push
main    → ci → build & push в ghcr.io/bx-shef/get-task-from-b24:latest
сервер  → Watchtower видит новый образ (~5 мин) → перезапускает контейнер
```

⚠ **Деплой гейтится зелёным `ci`** (`needs: ci` у джобы деплоя): красная сборка не
доезжает до реестра, а значит и до сервера. Это единственное, что отделяет «сломал
тесты» от «сломал прод».

⚠ **Сторонние actions пинуются по полному SHA коммита**, а не по тегу: тег изменяем
владельцем действия, и подменённый тег выполняет чужой код на раннере с `GITHUB_TOKEN`.
Комментарий `# vX.Y.Z` рядом с SHA читает Dependabot и держит пины свежими — то есть
пиннинг ничего не стоит в сопровождении.

## Сервер

- Контейнер приложения за общим `nginx-proxy` + `acme-companion` (сеть `proxy-net`),
  TLS — Let's Encrypt. Reverse-proxy ставится на сервере один раз и обслуживает все
  проекты; здесь его не дублируем.
- `Watchtower` следит за образом и катит обновления сам. Как и reverse-proxy, он
  ставится на сервере **один раз** и обслуживает все проекты — в
  `docker-compose.prod.yml` его нет, у сервиса `app` только метка
  `com.centurylinklabs.watchtower.enable`.
- На сервере лежат ровно три файла: `docker-compose.prod.yml`, `Makefile`, `.env`.
  Репозитория и пакетного менеджера там нет.

## Команды на сервере — только через `make`

⚠ **Правило, а не пожелание.** Терминал у владельца бывает мобильным, а
продиктованная строка `docker compose …` не проверяема и живёт только в истории чата.
Любая операция обязана быть **одной вставляемой целью** `make`.

Порядок при добавлении операции:

1. скрипт в `scripts/` — чтобы он был проверяем, а не жил в истории чата
   (там уже лежит `smoke.sh` — проверка обработчика на безопасность и живучесть);
2. цель в `Makefile`, тянущая скрипт из репозитория по тому же `REF`, что и `self-update`
   (иначе `Makefile` обновится из одной ветки, а скрипты приедут из другой);
3. строка `## описание` над целью — между ними могут идти обычные `#`-комментарии,
   `make help` запоминает последнее описание и печатает его у ближайшей цели;
4. владельцу — `make self-update && make <цель>`.

**`make self-update` заводим первым.** `Makefile` кладётся на сервер один раз при
развёртывании и дальше живёт своей жизнью: без цели, которая обновляет его самого,
все остальные цели бесполезны. Скачанное проверяем **до** замены и сохраняем копию
прежнего — битый `Makefile` лишает сервер единственного интерфейса.

⚠ **Параметры `make` передаём ПЕРЕД командой** (`DAY=… make цель`), а не после.
Значение параметра, заданное как `make цель VAR=…`, раскрывается до всякого шелла —
включая режим `-n`: осторожный «сперва посмотрю, что будет» детонирует вместо того,
чтобы защищать. Параметр ветки (`REF`) поэтому задаётся в файле жёстко и из командной
строки не переопределяется.

## Первичное развёртывание

⚠ **A-запись `get-task-from-b24.bx-shef.by` должна указывать на сервер ДО подъёма** —
иначе acme-companion не выпустит сертификат, а без HTTPS Битрикс24 не примет форму
локального приложения у клиента.

```bash
mkdir -p /home/bitrix/get-task-from-b24 && cd /home/bitrix/get-task-from-b24

# 1. два файла из репозитория
curl -fsSLO https://raw.githubusercontent.com/bx-shef/get-task-from-b24/main/docker-compose.prod.yml
curl -fsSLO https://raw.githubusercontent.com/bx-shef/get-task-from-b24/main/Makefile

# 2. .env
cat > .env <<'ENV'
DOMAIN=get-task-from-b24.bx-shef.by
LETSENCRYPT_EMAIL=почта@владельца
POSTGRES_PASSWORD=<сильный случайный>

PUBLIC_BASE_URL=https://get-task-from-b24.bx-shef.by
B24_TARGET_WEBHOOK_URL=https://мой.bitrix24.ru/rest/1/<токен вебхука>/
B24_TARGET_RESPONSIBLE_ID=1
TELEGRAM_BOT_TOKEN=
TELEGRAM_CHAT_ID=
# Раскомментировать после «Разовой настройки нашего портала» ниже:
#B24_TARGET_UF_SOURCE_TASK=UF_SOURCE_TASK_ID
B24_PORTAL_01=client-one.bitrix24.ru,17,local.xxxxxxxx,xxxxxxxx
ENV
echo "B24_TOKEN_ENC_KEY=$(openssl rand -hex 32)" >> .env

# 3. поднять
make prod-up
make doctor
```

**Сервис не стартует без** `B24_PORTAL_*` (пустой реестр = отказ обслуживать всех, и
громкий отказ лучше молчания), `B24_TOKEN_ENC_KEY` (проверяется прогоном шифрования
прямо на старте), `DATABASE_URL`, `REDIS_URL`, `B24_TARGET_WEBHOOK_URL`,
`B24_TARGET_RESPONSIBLE_ID`, `PUBLIC_BASE_URL`.

**Переменные, при которых сервис стартует, но работает неправильно** — авария тихая и
отложенная, её находят по последствиям:

| Переменная | Что тихо ломается |
|---|---|
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` | задачи переносятся, но никто об этом не узнаёт. ⚠ Обе или ни одной — половина настроек роняет старт намеренно |
| `PUBLIC_BASE_URL` | указан с ошибкой → подписка `event.bind` уедет на неверный адрес: приложение установится, а события пойдут в никуда |
| `B24_TARGET_RESPONSIBLE_ID` | задачи создаются на не того сотрудника — они есть, но их никто не видит |
| `B24_TARGET_UF_SOURCE_TASK` | не задана → ID задачи клиента в задачу не пишется; задана до заведения поля → каждый перенос шлёт порталу несуществующий ключ |

⚠ **`B24_TOKEN_ENC_KEY` — не «просто ключ».** Потеряли или сменили — все 20–30 порталов
придётся переустанавливать у клиентов. Он идёт в бэкап вместе с базой и отдельно от неё.

## Разовая настройка нашего портала

Поле, куда сервис пишет ID задачи клиента, заводится один раз вебхуком:

```bash
cd /home/bitrix/get-task-from-b24
set -a; . ./.env; set +a
curl -s -X POST "${B24_TARGET_WEBHOOK_URL%/}/task.item.userfield.add.json" \
  -H 'content-type: application/json' \
  -d '{"PARAMS":{"FIELD_NAME":"SOURCE_TASK_ID","USER_TYPE_ID":"double","MULTIPLE":"N","EDIT_FORM_LABEL":{"ru":"ID задачи у клиента"},"XML_ID":"GET_TASK_FROM_B24_SOURCE_ID"}}'
```

В ответе придёт `{"result":<id поля>}`. После этого — раскомментировать в `.env`:

```
B24_TARGET_UF_SOURCE_TASK=UF_SOURCE_TASK_ID
```

и применить: `make prod-redeploy`.

⚠ **Второй раз не запускать.** Повторный вызов заведёт ВТОРОЕ поле с кодом
`UF_SOURCE_TASK_ID1`, а переменная будет указывать на первое — сервис продолжит писать
не туда, куда смотрит человек. Проверить, что уже заведено:
`curl -s -X POST "${B24_TARGET_WEBHOOK_URL%/}/task.item.userfield.getlist.json" -d '{}'`.

⚠ **Адрес вебхука — секрет**, а `set -a; . ./.env` кладёт его в окружение сессии, но не
в history. Не подставляйте его в командную строку руками.

⚠ Префикс `UF_` Битрикс24 добавляет сам — итоговый код поля `UF_SOURCE_TASK_ID`, его и
кладём в `B24_TARGET_UF_SOURCE_TASK`. Тип `double` — единственный числовой из четырёх,
которые принимает метод (`string`, `double`, `datetime`, `boolean`).

⚠ **Поле пригодно для чтения человеком, но не для поиска.** Замерено на боевом портале:
фильтр `tasks.task.list` по этому полю находит ноль задач при существующем значении, а
в camelCase молча возвращает всё подряд. Не стройте на нём сверку — для этого есть
журнал `transfers` (`make transfers`).

✅ Заведено на нашем портале 2026-08-26, проверено записью и чтением.

## Подключение и отключение клиентов

Реестр порталов правится целями `make`, а не руками: строка длинная, ошибка в ней тихая.

⚠ **Сперва `make self-update`.** `Makefile` кладётся на сервер один раз и сам себя не
обновляет, поэтому цели `client-*` появятся там только после него.

```bash
make self-update
DOMAIN=portal.example.by RESPONSIBLE=17 CLIENT_ID=local.xxx CLIENT_SECRET=yyy GROUP=0 make client-add
make clients          # кто подключён (секреты не печатаются)
DOMAIN=portal.example.by make client-disable   # обратимо: строка комментируется
DOMAIN=portal.example.by make client-enable
DOMAIN=portal.example.by CONFIRM=1 make client-forget  # необратимо: удаляет токены из базы
make prod-redeploy    # применить правки .env
```

⚠ **Параметры передаются ПЕРЕД `make`.** Значение, заданное как `make цель VAR=…`,
раскрывается до всякого шелла — включая режим `-n`, то есть осторожный «сперва
посмотрю» детонирует вместо того, чтобы защищать.

⚠ **`client-disable` оставляет токены портала в базе** — отключение обратимо. Убрать
доступы совсем — `client-forget`, и тогда вернуть портал сможет только сам клиент
переустановкой приложения.

## Эксплуатация

| Команда | Зачем |
|---|---|
| `make doctor` | живо ли: контейнеры + `/health` |
| `make transfers` | последние 20 записей журнала переносов — что доехало, что нет |
| `make portals` | какие порталы установлены и когда продлевались токены |
| `make clients` | кто в реестре, с какой группой, кто отключён |
| `make logs-tail` | последние 50 строк лога без слежения — для мобильного терминала |
| `make logs` | логи приложения |
| `make prod-redeploy` | подтянуть свежий образ вручную |
| `make backup` | дамп базы (токены порталов + журнал) |

## Откат

Watchtower катит `latest`, поэтому откат — это закрепить предыдущий тег:

```bash
# в docker-compose.prod.yml заменить :latest на :sha-<коммит>
CONFIRM=1 make compose-update   # если правку уже смержили в main
make prod-redeploy
make doctor
```

⚠ Откатывать **вместе с базой** нельзя бездумно: миграции идемпотентны и только
добавляют, поэтому старый образ на новой схеме работает. Обратное — новый образ на
старой схеме — тоже работает, миграции гоняются на старте.
