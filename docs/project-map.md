## Цель

Сетевой обработчик, который ловит создание задачи на портале клиента Битрикс24,
проверяет критерии и заводит задачу в нашем Битрикс24 + шлёт сигнал в Telegram.
Порталов клиентов — **20–30**, список в переменных окружения.

Критерии, перенос полей и поведение при ошибках — [`PROCESSING.md`](PROCESSING.md).

## Что мешает запуску

Кода это больше не касается — всё упирается в доступы и сервер:

- ✅ **DNS**: домен создан владельцем 2026-08-26; на сервере уже есть `proxy-net` и
  Watchtower от соседних проектов, каталог `/home/bitrix/get-task-from-b24` заведён.
  ⚠ Адрес попадает в форму локального приложения у **каждого** клиента, и смена адреса
  потом требует участия каждого из них.
- ⛔ **Вебхук нашего Б24** (право `task`) и id сотрудника-исполнителя.
- ⛔ **Первый портал клиента**: `client_id`/`client_secret` локального приложения и id
  «особого» исполнителя.
- ⛔ **Telegram**: токен бота и `chat_id`.
- ⬜ Настройки GitHub из [`REPO_SETUP_CHECKLIST.md`](REPO_SETUP_CHECKLIST.md) (защита
  `main`, `ci` как required-check) — владелец делает 2026-08-27.
- ⬜ Образ появится в GHCR только после мержа PR: джоба `deploy` идёт с `main`.
- ⬜ **Замер до первого клиента:** название скоупа задач (`task` против `tasks`) и
  форма обмена refresh-токена (POST против GET) — документация Битрикс24 противоречива,
  а цена промаха отложенная.
