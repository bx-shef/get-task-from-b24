## Цель

**Система работы с обращениями** ([`PRODUCT.md`](PRODUCT.md)): клиент создаёт обращение
у себя в Битрикс24, оно становится задачей у нас и issue на GitHub, проходит цикл
разработки, а по итогам месяца превращается в счёт.

Сегодня в бою — **транспорт**: событие о создании задачи на портале клиента доезжает до
задачи в нашем Битрикс24 и сигнала в Telegram. Это этап 0 из
[`ROADMAP.md`](ROADMAP.md); критерии и поведение при ошибках —
[`PROCESSING.md`](PROCESSING.md).

## План работ

Ближайшие пять PR по порядку. Каждый — слайс: код + тесты + документация в одном PR,
панель из 5 проверяющих в два цикла, зелёный CI, squash-merge ([`PROCESS.md`](PROCESS.md)).

| # | PR | Зачем именно сейчас | Готово, когда |
|---|---|---|---|
| **P1** | Переезд на `@bitrix24/b24jssdk` | всё, что напишем дальше, иначе придётся переписывать на SDK | вызовы портала идут через `B24Hook`/`B24OAuth`, продление токенов работает на живом портале, `pnpm check` зелёный |
| **P2** | Снятие журнала переносов | связка теперь живёт в UF-полях, журнал стал вторым местом за тем же фактом | задача не переносится дважды, сверка после создания удаляет лишнее, `transfers` и её миграция убраны |
| **P3** | Кнопка «Отправить в sh-support-bx» | пока клиент один, обновление приложения стоит дёшево | человек нажал кнопку в задаче на портале клиента — задача приехала к нам |
| **P4** | Прототипы механик (инкремент 1.0) | схема переписки не окончательная, а на ней стоит весь этап 1 | пункт меню виден в чате задачи и в мобильном; GitHub App шлёт вебхуки на наш сервер |
| **P5** | Реестр в смарт-процессах (инкремент 1.1) | реестр в окружении не масштабируется на 20–30 клиентов | клиент и проект резолвятся по порталу, скрипт заводит смарт-процессы воспроизводимо |

**P1 — переезд на SDK.** `B24Hook` для нашего портала по вебхуку, `B24OAuth` с продлением
токенов для порталов клиентов. В том же PR решается судьба `src/notify/telegram.ts`:
`TelegramHandler` в SDK есть, но текст сообщения он вставляет в HTML-разметку без
экранирования (замер в [`../CLAUDE.md`](../CLAUDE.md)) — берём только со своим
экранированием либо оставляем свой модуль.

**P2 — снятие журнала.** «Переносилась ли задача» спрашивается у портала по паре
`UF_SOURCE_TASK_ID` + `UF_SOURCE_DOMAIN`. Хранилища отказов не заводим: очередь и есть
механизм надёжности. Защита от задвоения — сверкой **после** создания, с удалением лишней
задачи и сигналом в Телеграм. Идёт после P1: журнал трогает те же вызовы портала, которые
переезжают на SDK. Разбор — [`PRODUCT.md`](PRODUCT.md), раздел 1а.

**P3 — кнопка в карточке задачи.** Ручной путь для случая, когда сервис не работал и
событие не пришло вовсе. Точка встраивания `TASK_VIEW_TAB`, регистрация `placement.bind`.
⚠ Требует скоупа `placement`, то есть **обновления приложения у каждого клиента** —
поэтому чем раньше, тем дешевле. Разбор — [`PRODUCT.md`](PRODUCT.md), раздел 1б.

⚠ **Почему P3 идёт раньше прототипов**, хотя в [`ROADMAP.md`](ROADMAP.md) инкремент 1.0
стоит перед 1.0б: та таблица упорядочена по продуктовому риску, а этот план — по
техническим зависимостям и цене промедления. Кнопка меняет состав прав приложения, и
каждый следующий подключённый клиент добавляет к ней ручную работу. Прототипы такой
цены не имеют и от задержки не дорожают. **Очерёдность PR задаётся здесь**, в этом
плане, — чтобы у неё было одно место.

**P4 и P5** — первые два инкремента этапа 1 из [`ROADMAP.md`](ROADMAP.md).

## Что мешает

**Блокеров нет: все развилки закрыты владельцем 2026-08-27.**

- ✅ **Домен** — остаётся `get-task-from-b24.bx-shef.by`; спецификационный
  `support.bx-shef.by` не используем.
- ✅ **Хранилище связки (Б2)** — UF-поля задач, и это **замерено** на боевом портале
  ([`PRODUCT.md`](PRODUCT.md), раздел 1). Журнал переносов после этого убирается;
  Postgres остаётся ради токенов порталов.
- ✅ **Маркетплейс** — не скоро; проектировать под него сейчас не нужно.

Мелочь, не блокирующая ничего:

- ⬜ Неверный id группы портал молча принимает: `make client-add` проверяет только, что
  это число. Ошибка вскроется задачами в чужой группе — смотреть `groupId` в строке
  лога `created`.
- ⬜ **Замер ждёт своего часа:** форма обмена refresh-токена (POST против GET) вскроется
  примерно через час после установки, когда токен впервые протухнет.
- ⬜ **Префикс `#support`** — общий на всех клиентов или свой у каждого. Вопрос живёт
  ровно до инкремента 1.2: с формой префикс исчезает как понятие.
